# 05. 네이티브 클라이언트 앱 아키텍처

## 1. 확정된 구성

**Windows와 Android 모두 각 플랫폼의 네이티브 UI 프레임워크로 개발하고, 비 UI 로직은 공유 Rust 코어 라이브러리로 통합합니다.**

| 계층 | Windows | Android |
|-|-|-|
| UI | **WinUI 3 / Windows App SDK** (C#, .NET 8) | **Jetpack Compose** (Kotlin, Android SDK) |
| 바인딩 | C FFI → C# `DllImport` (P/Invoke) | C FFI → JNI (`uniffi-rs` 생성) |
| 코어 | **`civicagora-core` (Rust, `.dll`)** | **`civicagora-core` (Rust, `.so`)** |
| 보안 저장소 | Windows Hello / DPAPI | Android Keystore (StrongBox 우선) |
| 배포 | MSIX (Microsoft Store + 사이드로드) | AAB (Google Play + APK 직배포) |

웹뷰를 감싸는 방식(Electron, Tauri 등)은 "네이티브 앱" 요구에 부합하지 않아 채택하지 않았습니다(→ D14).

### 1.1 왜 UI는 나누고 코어는 합치는가

UI를 플랫폼별로 나누는 비용은 감수할 만합니다. 반면 **P2P·암호·ZK 로직까지 두 번 구현하는 것은 감수할 수 없습니다.** 합의 규칙이나 서명 방식이 두 구현체 사이에서 미세하게 어긋나면 네트워크가 갈라지고, 그 버그는 재현조차 어렵습니다.

공유 코어는 다음을 모두 담당합니다.

* Secp256k1 키 관리, DID 생성, 문서 서명·검증
* ZK 증명 생성 (Circom 회로 + rapidsnark)
* rust-libp2p 노드 구동 — GossipSub, Kademlia DHT, AutoNAT, DCUtR
* Ceramic ComposeDB 클라이언트, 스트림 검증
* 로컬 캐시(SQLite), 오프라인 작성 큐
* 머클 증명 검증 (온체인 루트 대조)
* Step 1 온디바이스 유해성 스크리닝 (ONNX Runtime)

UI 계층이 담당하는 것은 화면, 입력, 플랫폼 통합(알림·공유·생체인증)뿐입니다.

### 1.2 바인딩 생성

코어의 공개 인터페이스는 **UDL(`civicagora.udl`)에 한 번만 정의**하고 `uniffi-rs`로 Kotlin·C# 바인딩을 자동 생성합니다. 손으로 쓴 FFI 래퍼는 두 플랫폼이 어긋나는 가장 흔한 원인이므로 금지합니다.

```
civicagora-core/
├── src/
│   ├── identity.rs      # 키·DID·ZK 증명
│   ├── p2p.rs           # libp2p 노드
│   ├── store.rs         # Ceramic 클라이언트 + SQLite 캐시
│   ├── moderation.rs    # Step 1 온디바이스 스크리닝
│   └── lib.rs
├── civicagora.udl       # 단일 인터페이스 정의
└── bindings/
    ├── kotlin/          # 자동 생성
    └── csharp/          # 자동 생성
```

## 2. 네이티브가 필수인 이유

이 프로젝트에서 네이티브 선택은 취향이 아니라 요구사항에서 도출됩니다.

### 2.1 ZK 증명 생성 성능

Groth16 증명 생성은 무거운 연산입니다. 브라우저 Wasm(SnarkJS)에서 모바일 기기로 실행하면 수십 초가 걸려 가입 이탈이 발생합니다. 네이티브 rapidsnark는 동일 회로를 **수 초 이내**에 처리하며, 멀티코어와 NEON/AVX를 활용할 수 있습니다.

### 2.2 장시간 P2P 연결

GossipSub 피어 연결은 지속적으로 유지되어야 합니다. 웹 환경에서는 탭이 닫히면 노드가 사라지고 WebRTC 외의 전송 수단이 제한됩니다. 네이티브 앱은 QUIC·TCP를 직접 쓰고, Android 포그라운드 서비스로 연결을 유지할 수 있습니다.

### 2.3 개인키 보호

복구 불가능한 신원 키를 브라우저 저장소에 두는 것은 적절하지 않습니다. 네이티브 앱은 Android Keystore(StrongBox)와 Windows Hello에 키를 위임해 **키가 앱 메모리로 나오지 않게** 할 수 있습니다. 서명은 보안 하드웨어 안에서 수행됩니다.

### 2.4 온디바이스 톤 코칭

Step 1 스크리닝이 단말에서 돌면 **타이핑 중인 내용이 서버로 전송되지 않습니다.** 정치적 의견을 다루는 플랫폼에서 이 차이는 결정적입니다.

## 3. Android 특수 고려사항

### 3.1 백그라운드 동기화

Android의 배터리 최적화는 장시간 소켓 연결에 적대적입니다.

| 상태 | 동작 |
|-|-|
| 포그라운드 | 전체 GossipSub 참여. 구독 안건 실시간 수신 |
| 백그라운드 (포그라운드 서비스 허용) | 구독 안건 헤더만 동기화. 지속 알림 표시 |
| 백그라운드 (권한 없음) | `WorkManager`로 15분 주기 폴링. 본문은 열람 시 조회 |
| Doze 모드 | 연결 해제. 복귀 시 일괄 동기화 |

포그라운드 서비스 사용은 사용자에게 명시적으로 동의를 받고 언제든 끌 수 있게 합니다. Google Play 정책상 포그라운드 서비스 유형 선언(`dataSync`)과 사용 사유 제출이 필요합니다.

### 3.2 저장 용량

전체 IPFS 블록스토어를 모바일에 두는 것은 비현실적입니다.

* 기본값은 **부분 복제**입니다. 구독 안건과 최근 열람 콘텐츠만 보관합니다.
* 블록스토어 상한(기본 500MB)을 설정에서 조절할 수 있고, 초과 시 LRU로 제거합니다.
* "전체 노드 모드"는 옵션으로 제공하되 Wi-Fi + 충전 중에만 동작합니다.

### 3.3 스토어 정책

* 앱은 암호화폐를 거래하지 않습니다. SBT 배지는 **양도·판매 불가**이며 금전적 가치가 없음을 스토어 설명과 앱 내에 명시합니다.
* 사용자 생성 콘텐츠를 다루므로 신고 기능, 차단 기능, 연락 수단을 반드시 노출합니다. 블라인드 체계가 이 요구를 충족합니다.
* 정치 콘텐츠 앱은 심사가 길어질 수 있으므로 배포 일정에 여유를 둡니다.

## 4. Windows 특수 고려사항

* **방화벽**: 첫 실행 시 인바운드 연결 허용 프롬프트가 뜹니다. 설치 과정에서 미리 안내하고, 거부해도 릴레이 경유로 동작하도록 폴백합니다.
* **자동 시작**: 선택 사항으로 제공합니다. 기본값은 꺼짐입니다.
* **MSIX 서명**: Store 배포와 별도로 사이드로드용 서명 빌드를 제공합니다. 탈중앙 플랫폼이 특정 스토어의 심사에 완전히 종속되면 원칙에 어긋나기 때문입니다.
* **접근성**: WinUI 3의 자동화 속성을 채우고 화면 낭독기 탐색을 검증합니다. 3열 레이아웃은 스크린 리더에서 순서가 혼동되기 쉬우므로 열 제목을 랜드마크로 노출합니다.

## 5. 화면 구성

두 플랫폼이 동일한 정보 구조를 공유하되 레이아웃은 플랫폼 관행을 따릅니다.

| 화면 | Windows | Android |
|-|-|-|
| 안건 목록 | 좌측 내비게이션 + 목록 | 하단 탭 + 목록 |
| **3열 토론** | 3열 동시 표시 | 스와이프 탭 3개 (찬성 / 대안 / 반대) |
| 카드 작성 | 모달 다이얼로그 | 전체 화면 |
| 톤 코칭 배너 | 입력 필드 하단 인라인 | 입력 필드 하단 인라인 |
| 여론 지형도 | 우측 패널 상시 | 별도 탭 |
| 랭킹·프로필 | 좌측 내비게이션 | 하단 탭 |

**모바일의 3열 처리가 설계상 가장 중요한 지점입니다.** 화면이 좁다고 "찬성/반대"만 탭으로 두고 대안 열을 숨기면 브리징이라는 제품의 핵심이 보이지 않게 됩니다. 따라서 Android에서는 **가운데 '대안·합의' 탭을 기본 진입 탭**으로 두고, 합의 배너를 안건 상세 최상단에 탭과 무관하게 고정 노출합니다.

## 6. 웹 surface의 위치

기존 로드맵의 Next.js 웹은 **읽기 전용 열람·연구 포털**로 역할을 축소합니다.

* 검색엔진 색인과 외부 링크 공유(기자·연구자 접근 경로)를 담당합니다.
* 안건·카드 열람, 여론 지형도, 랭킹, 오픈 데이터 다운로드를 제공합니다.
* **작성·반응·가입은 제공하지 않습니다.** 이들은 개인키와 P2P 노드를 요구하므로 네이티브 앱에서만 가능합니다.

> 웹에서도 작성이 가능해야 하는지는 미결 사항입니다. 허용하려면 키를 브라우저에 두거나 서버 위임 서명이 필요한데, 둘 다 신원 모델의 보안 가정을 약화시킵니다. Phase 3 착수 전에 결정해야 합니다.

## 7. 저장소 구조 (예정)

```
openAgora/
├── core/                    # Rust 공유 코어 + UDL
├── apps/
│   ├── windows/             # WinUI 3 (C#, .NET 8)
│   └── android/             # Jetpack Compose (Kotlin)
├── web/                     # Next.js 15 읽기 전용 포털
├── services/
│   ├── moderation/          # FastAPI + vLLM 톤 코칭
│   ├── bridging/            # 행렬 분해 · Pol.is 배치 잡
│   └── openapi/             # 연구자 오픈 데이터 API
├── circuits/                # Circom ZK-Email 회로
├── contracts/               # Solidity + Foundry
├── maindocs/                # 본 명세서 (단일 진실 공급원)
└── docs/                    # 아카이브 (비권위)
```
