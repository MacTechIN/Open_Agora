# 12. 온체인 계층 — 직접 만들 것과 가져다 쓸 것

**질문**: 블록체인 모듈을 직접 만들지 말고 기존 서비스를 쓰면 어떤가?

**답**: 대체로 옳습니다. 특히 **신뢰 설정(trusted setup)을 직접 하지 않는 것**은 노력 절감이 아니라 **보안 요구사항**으로 다뤄야 합니다. 다만 전부를 외부에 맡길 수는 없고, 경계를 정확히 그어야 합니다.

> 이 문서의 사실 확인은 2026-09-21 기준입니다. §6에 **확인하지 못한 항목**을 따로 표시했습니다. 그중 하나는 이 질문보다 더 큰 위험입니다.

---

## 1. 온체인 계층이 실제로 하는 일

`01_ARCHITECTURE.md`의 계층 4는 네 가지를 합니다. 각각을 따로 판단해야 합니다.

| # | 역할 | 기존 설계 | 실제로 필요한 것 |
|-|-|-|-|
| A | ZK-Email 증명 검증 | Circom 회로 + 자체 신뢰 설정 | 검증된 회로와 이미 끝난 세리머니 |
| B | 1인 1계정 전역 유일성 | `nullifierRegistry` 매핑 | 중복 없는 집합 |
| C | 상태 머클 루트 앵커링 | `policyAnchors` + 제출기 | 데이터가 시점 T에 존재했고 변조되지 않았다는 증명 |
| D | 평판 마일스톤 배지 | 자체 SBT 컨트랙트 | 양도 불가 증명서 발급 |

§5(모델 가중치 CID 앵커링)도 C와 같은 성격입니다.

## 2. 가장 강한 근거 — 신뢰 설정을 직접 하지 마라

`09_DEVELOPMENT_PLAN.md`의 VS-C1은 "Circom ZK-Email 검증 회로 구현 및 **신뢰 설정**"을 요구합니다. 이것이 이 저장소에서 **가장 위험한 한 줄**입니다.

Groth16 신뢰 설정은 세리머니 과정에서 생기는 부산물(toxic waste)을 모든 참여자가 폐기해야 안전합니다. 하나라도 보관하면 **유효한 증명을 위조**할 수 있습니다. 이 플랫폼에서 증명 위조는 곧 **가짜 시민을 무한히 만들 수 있다**는 뜻이고, 브리징 알고리즘이 방어하는 몰표를 훨씬 더 근본적인 층위에서 무력화합니다.

더 나쁜 점은 **탐지가 불가능하다**는 것입니다. 위조된 증명은 정상 증명과 수학적으로 구별되지 않습니다. 감사 로그에도, 온체인 기록에도 아무 흔적이 남지 않습니다.

소규모 팀이 세리머니를 운영하면 "우리는 폐기했다"는 주장에 의존하게 됩니다. 이 프로젝트는 **운영자를 신뢰하지 않는 것이 존재 이유**이므로, 그 주장을 시민에게 요구하는 순간 자기모순입니다.

따라서 **다수가 참여한 공개 세리머니의 결과물을 물려받는 것이 유일하게 일관된 선택입니다.** 이것은 편의가 아니라 원칙의 문제입니다.

## 3. 후보별 평가

### 3.1 A·B — ZK-Email 검증과 유일성

**확인된 사실**

* `zkemail/zk-email-verify` — 활성 저장소. DKIM 검증 Circom 라이브러리와 온체인 검증 컨트랙트를 제공합니다. `ref_docs/research.md`가 이미 선정했던 것이며, 우리가 쓸 계획이었던 것은 **회로였지 세리머니가 아니었습니다.**
* **Semaphore V4** — Ethereum, **Arbitrum**, **Polygon**, Optimism, Base, Linea, Gnosis 메인넷과 8개 테스트넷에 배포되어 있습니다. 배포마다 `Semaphore`, `SemaphoreVerifier`, `PoseidonT3` 세 컨트랙트를 포함합니다. 우리가 후보로 둔 L2 두 곳 모두에 이미 있습니다.

**구성 방식**

```
이메일 소유 증명   →  zk-email 회로 (DKIM 서명 검증)
       │                검증된 회로. 우리가 쓰지 않는다
       ▼
이메일 중복 방지   →  Nullifier = Poseidon(Email, AppSalt) 집합
       │                여기만 우리 몫이 남는다 (§4)
       ▼
익명 참여          →  Semaphore 그룹 가입 + 행위별 nullifier
                        배포된 컨트랙트 사용. 우리가 배포하지 않는다
```

Semaphore는 "그룹 구성원임을 밝히지 않고 증명하고, 같은 scope에서 두 번 행동하지 못하게" 합니다. 우리의 **익명 참여**와 정확히 맞습니다. 다만 "같은 이메일로 두 번 가입 불가"는 Semaphore의 책임이 아니라 **그룹에 넣어줄 때 판단할 문제**입니다(§4).

### 3.2 C — 앵커링

**확인된 사실**: Ceramic은 **Self-Anchoring**을 제공합니다 — "Run your own anchor service on any EVM blockchain."

즉 우리 데이터 계층이 **이미 앵커링을 포함**합니다. 스트림을 머클 배칭해 EVM 체인에 앵커링하는 일을 Ceramic이 합니다. `policyAnchors` 컨트랙트와 제출기를 따로 만들 이유가 약해집니다.

다만 정직하게 말하면, **self-anchoring은 우리가 앵커 서비스를 운영한다는 뜻**입니다. 중앙화 지점이 사라지는 게 아니라 위치가 바뀝니다. 이 점은 §5에서 다시 다룹니다.

### 3.3 D — 배지

**확인된 사실**: EAS(Ethereum Attestation Service)가 **Optimism**, **Base**(`0x4200…0021` EAS, `0x4200…0020` SchemaRegistry), **Arbitrum One**, **Arbitrum Nova**에 배포되어 있습니다.

배지 다섯 종은 **스키마 등록 + 증명서 발급**으로 충분합니다. 컨트랙트를 쓰지 않고 스키마를 정의합니다. 양도 불가·취소 정책도 EAS의 기능으로 표현됩니다.

## 4. 그래도 남는 것 — 정직한 경계

외부로 다 밀 수는 없습니다. 남는 것은 하나입니다.

**이메일 Nullifier 집합.** "이 이메일로 이미 가입했는가"를 전역적으로 판정하는 중복 없는 집합이 필요합니다. Semaphore의 nullifier는 *행위 중복*을 막지 *가입 자격 중복*을 막지 않습니다. 이 둘은 다른 문제입니다.

그런데 이것은 "블록체인 모듈"이라고 부를 만한 것이 아닙니다.

```solidity
mapping(bytes32 => bool) public consumed;

function consume(bytes32 nullifier, bytes calldata proof, uint256[] calldata signals) external {
    require(!consumed[nullifier], "already registered");
    require(verifier.verifyProof(proof, signals), "invalid proof");
    consumed[nullifier] = true;
    semaphore.addMember(GROUP_ID, signals[IDENTITY_COMMITMENT_INDEX]);
}
```

**검증기와 그룹 관리를 모두 외부에 맡기고 나면, 우리 코드는 집합 하나와 호출 두 번입니다.** 감사 표면이 컨트랙트 한 개의 함수 하나로 줄어듭니다. 이것이 자체 구현을 줄여서 얻는 진짜 이득입니다 — 코드를 덜 쓰는 것이 아니라 **틀릴 수 있는 곳을 줄이는 것**입니다.

zk-email이 자체 nullifier 레지스트리를 제공한다면 이마저도 불필요할 수 있습니다. §6의 확인 항목입니다.

## 5. 새로 생기는 위험 — 그리고 그 대칭성

의존은 공짜가 아닙니다. 다만 **어느 쪽도 중앙화를 피하지 못한다**는 점을 분명히 해야 합니다.

| 위험 | 자체 구현 | 기존 서비스 |
|-|-|-|
| 신뢰 설정 오염 | **우리가 책임진다. 탐지 불가** | 대규모 공개 세리머니를 물려받는다 |
| 컨트랙트 버그 | 우리 감사 비용. 실전 검증 없음 | 다수 프로젝트가 쓰는 실전 검증 |
| 프로토콜 폐기·변경 | 없음 | **있다. 대응 계획 필요** |
| 앵커 서비스 운영 | 우리가 제출기를 운영 | self-anchoring도 우리가 운영 |
| 체인 선택 종속 | 우리가 결정 | 배포된 체인으로 제약됨 |

세 번째가 유일하게 순수한 신규 위험입니다. 완화책은 **인터페이스 뒤에 두는 것**입니다. `11_SOVEREIGN_JUDGMENT.md` §8에서 판단 실행자에 적용한 것과 같은 방식입니다.

```
IdentityRegistry  (우리 인터페이스)
   ├── SemaphoreBackedRegistry   기본값
   └── StandaloneRegistry        폐기 대비 최소 구현
AttestationSink
   ├── EasAttestationSink        기본값
   └── LocalAttestationSink      폐기 대비
```

대비 구현을 **미리 만들지는 않습니다.** 인터페이스만 지켜두고, 실제로 필요해질 때 씁니다. 쓰지 않을 코드를 미리 쓰는 것은 그 자체로 비용입니다.

그리고 다섯 번째가 미결 사항 하나를 자동으로 좁힙니다. `08_DECISIONS.md`의 "L2 체인 최종 선택"은 이제 **Semaphore와 EAS가 모두 배포된 체인**이라는 조건을 갖습니다. 확인된 범위에서 **Arbitrum One이 두 조건을 동시에 만족**합니다.

## 6. 확인하지 못한 것

아래는 **주장이 아니라 확인 항목**입니다. 채택 결정 전에 해소해야 합니다.

| # | 항목 | 왜 중요한가 |
|-|-|-|
| 1 | **Semaphore 신뢰 설정 세리머니의 규모·완료 여부·키 공개 위치** | §2의 논거 전체가 여기 달려 있다. 확인한 문서 페이지들에 세리머니 언급이 없었다. 공개 세리머니가 아니라면 이 문서의 결론이 바뀐다 |
| 2 | **ComposeDB의 현재 지원 상태** | 아래 별도 설명 |
| 3 | zk-email의 자체 nullifier 레지스트리 제공 여부 | 제공한다면 §4의 남은 코드마저 사라진다 |
| 4 | EAS의 Polygon 배포 여부 | 확인한 범위는 Optimism·Base·Arbitrum이다 |
| 5 | Semaphore 그룹 관리자 권한 모델 | 그룹에 멤버를 추가하는 권한이 누구에게 있는지에 따라 중앙화 지점이 생긴다 |

### 6.1 ComposeDB — 이 질문보다 큰 위험

확인 과정에서 예상하지 못한 것이 나왔습니다. **현재 Ceramic 개발자 문서에 ComposeDB가 등장하지 않습니다.** 문서는 Rust 기반 **Ceramic One**, Ceramic SDK, Flight SQL 기반 쿼리 파이프라인을 중심으로 재편되어 있습니다. `ceramicstudio/js-composedb` 저장소는 아카이브 상태가 아니지만 스타 94개로 활발하다고 보기 어렵습니다.

이것이 중요한 이유는 `01_ARCHITECTURE.md` §3이 **ComposeDB GraphQL 스키마로 데이터 모델 전체를 정의**하고 있기 때문입니다. `Policy`·`DebateCard`·`Reply`·`Reaction` 네 모델과 `accountRelation: SET`을 이용한 반응 유일성 강제가 모두 ComposeDB 기능입니다.

ComposeDB가 유지보수만 되는 상태라면, **VS-B2(Ceramic 영속화)에 착수하기 전에 데이터 계층 스택을 재검토**해야 합니다. 이것은 온체인 모듈을 만들지 말지보다 임계 경로에 더 가까운 문제입니다.

이 항목을 `08_DECISIONS.md`의 미결 사항에 추가합니다.

## 7. 결론과 개발계획 반영

**채택합니다.** 단, §6이 해소된 뒤에 확정합니다.

| 슬라이스 | 기존 | 변경 |
|-|-|-|
| **VS-C1** | Circom 회로 구현 + **자체 신뢰 설정** | zk-email 회로 통합 + **증명 생성 성능 실측만**. 세리머니를 하지 않는다 |
| **VS-C2** | `CivicAgoraCore` 전체 배포 | Semaphore 연동 + **nullifier 집합 컨트랙트 하나** |
| **VS-F6** | 자체 앵커링 컨트랙트 + 제출기 | Ceramic self-anchoring 구성 + 재현 검증 도구 |
| **VS-G5** | 자체 SBT 컨트랙트 | EAS 스키마 5종 등록 + 발급 |
| **신규 VS-C0** | — | **§6 확인 슬라이스.** 세리머니·ComposeDB·nullifier·체인 배포 확인. 규모 S. **Phase 1의 첫 작업** |

VS-C1에서 세리머니가 빠지는 것이 가장 큰 변화입니다. 일정으로는 Phase 1이 짧아지고, 보안으로는 **우리가 책임질 수 없는 종류의 위험이 사라집니다.**

그리고 VS-C0을 Phase 1 맨 앞에 둡니다. 확인 없이 진행하면, 전제가 틀렸을 때 되돌릴 거리가 매주 길어집니다.
