# 10. AI 판단 지점 설계 (TypeSafe System One)

`03_ALGORITHMS_AI.md`는 AI 단계를 "프롬프트를 보내고 JSON을 파싱한다"로 규정했습니다. 이 문서는 그중 **판단(judgment)에 해당하는 부분을 타입이 보장되는 구조화 결정으로 재설계**합니다. 생성(generation)에 해당하는 순화문 작성은 그대로 생성 모델이 맡습니다.

> 본 문서는 설계안이며, §6의 두 가지 충돌이 해소되기 전에는 채택되지 않습니다.

---

## 1. 무엇이 문제였는가

기존 순화 프롬프트(`03_ALGORITHMS_AI.md` §3.3)는 한 번의 호출로 세 가지를 동시에 요구합니다.

```json
{
  "toxicity_score": 0.82,
  "detected_violations": ["비아냥/조롱", "인신공격"],
  "suggested_revision": "..."
}
```

여기에는 세 가지 결함이 있습니다.

1. **판단과 생성이 섞여 있습니다.** 생성 모델에게 자기 점수를 스스로 매기게 하는 구조인데, 생성 모델의 자기 신고 점수는 보정(calibration)되어 있지 않습니다. 0.82라는 숫자에 확률적 의미가 없습니다.
2. **파싱이 실패할 수 있습니다.** 모델이 JSON을 벗어나면 그 글은 판정 불능이 됩니다. 정치적 발언을 다루는 시스템에서 "판정 불능"은 조용한 통과 또는 조용한 차단이 되며, 어느 쪽이든 사고입니다.
3. **감사(audit)가 불가능합니다.** `04_REPUTATION_MODERATION.md` §3.2는 모든 중재를 공개 로그로 남겨 **진영별 편향을 통계적으로 검증**할 수 있어야 한다고 요구합니다. 그런데 자유 서술 JSON은 사후에 재검증할 수 있는 형태가 아닙니다.

---

## 2. 재설계 원칙

TypeSafe의 System One 모델은 자유 텍스트 대신 **타입이 정해진 판단과 확률**을 돌려줍니다. 코드가 워크플로를 소유하고, 모델은 의미 이해가 필요한 좁은 지점에만 등장합니다.

| 계층 | 담당 |
|-|-|
| **코드** | 제어 흐름, 임계치, 정책 결정, 점수 가감, 기록 |
| **판단 모델** | "이 문장이 인물을 공격하는가" 같은 좁은 의미 판단 |
| **생성 모델** | 순화문 작성 (판단 결과가 필요하다고 말한 뒤에만) |

**핵심 이득은 정책과 판단의 분리입니다.** 원시 판단값을 그대로 기록해 두면, 임계치를 바꿔도 재추론이 필요 없고, 제3자가 **같은 판단값에 같은 정책을 적용해 같은 결정이 나오는지 재계산**할 수 있습니다. 이것이 §1의 세 번째 결함에 대한 직접적인 해답입니다.

## 3. 판단 카탈로그

### 3.1 토론 카드 작성 시 (단일 호출, 병렬 질문)

카드 하나에 대해 아래 질문을 **한 번의 요청으로 동시에** 던집니다. 질문들은 서로의 답을 보지 못하며 병렬로 처리됩니다.

**전달 상태(state)**

```json
{
  "policy": {
    "title": "탄력 근로제 및 지역 보조금 개선안",
    "core_question": "직종별 유연 적용을 어떤 조건에서 허용할 것인가"
  },
  "card": {
    "stance": "OPPOSE",
    "problem_definition": "…",
    "evidence_source": "…",
    "actionable_solution": "…"
  },
  "evidence": {
    "domain": "kostat.go.kr",
    "excerpt": "…근거 URL 문서에서 발췌한 본문…"
  }
}
```

**질문**

| ID | 유형 | 지시문 | 왜 이 유형인가 |
|-|-|-|-|
| `attack_target` | Choice | 이 글의 비판은 무엇을 향하는가 | 상호 배타적 범주 선택 |
| `is_personal_attack` | Noul | 특정 인물이나 정당을 인신공격하는 표현이 있는가 | 확률 자체가 임계치에 쓰임 |
| `norm_severity` | Score | 공론장 규범 위반 정도 | 정도의 문제이므로 순서 있는 척도 |
| `solution_is_actionable` | Noul | 해결책이 실행 가능한 메커니즘을 서술하는가 | Field 3 검증 규칙 |
| `evidence_relation` | Choice | 근거 문서가 주장과 어떤 관계인가 | 뒷받침/반박/무관 3분 |

`attack_target`의 criteria가 이 설계에서 가장 중요합니다. 명세가 요구하는 **"인물·정당 비방 vs 정책적 문제 지적" 분리**가 바로 이 질문이며, 기존 분류기(kor_unsmile)가 할 수 없던 판단입니다.

```python
"attack_target": Choice(
    instructions="이 글의 비판이 향하는 대상은 무엇인가?",
    criteria={
        "policy_substance": "정책의 내용, 설계, 예상 효과, 예산 근거를 문제 삼는다",
        "person_or_party": "정책이 아니라 특정 인물·정당·지지자 집단의 자질이나 동기를 문제 삼는다",
        "both": "정책 비판과 인물·집단 공격이 함께 있다",
        "neither": "비판이라고 볼 만한 내용이 없다",
    },
)
```

```python
"norm_severity": Score(
    instructions="이 글이 공론장 규범을 어느 정도로 벗어나는가?",
    criteria=[
        "정중하다. 강한 주장이지만 표현은 절제되어 있다",
        "거슬린다. 냉소나 비아냥이 있으나 논점은 유지된다",
        "모욕적이다. 상대를 깎아내리는 표현이 논점을 대체한다",
        "혐오표현이다. 집단 정체성을 근거로 비하한다",
    ],
)
```

Score의 각 수준이 **구체적 상황을 서술**한다는 점이 중요합니다. "보통/심각" 같은 라벨은 판단 기준이 되지 못합니다.

### 3.2 정책 결정은 코드가 한다

판단값을 받아 결정하는 것은 순수 함수입니다. 모델을 다시 부르지 않습니다.

```python
def decide(j: Judgments, policy: Policy) -> Decision:
    """원시 판단값에 정책을 적용한다. 부수효과 없음, 재현 가능."""

    # 인물 공격은 '보정된 강도'가 아니라 '대상의 성격' 문제다.
    # 따라서 severity 단독이 아니라 대상 판단과 결합한다.
    attacks_person = (
        j.is_personal_attack >= policy.attack_action        # 기본 0.70
        and j.attack_target in ("person_or_party", "both")
    )

    if attacks_person or j.norm_severity >= policy.severity_block:   # 기본 2.0
        return Decision.COACH          # 인라인 배너 + 순화문 생성

    if j.is_personal_attack >= policy.attack_review:        # 기본 0.35
        return Decision.RECORD_ONLY    # 회색지대: 경고 없이 통과, 기록만

    return Decision.PASS
```

기존 명세의 0.30 게이트와 0.65 배너 트리거는 그대로 살아 있습니다. `attack_review`(0.35)가 회색지대의 시작, `attack_action`(0.70)이 배너 트리거에 대응하며, **온디바이스 1차 게이트(0.30)를 통과한 글만 여기에 도달합니다.**

### 3.3 근거 URL 검증

`00_PRODUCT_SPEC.md` §3은 근거 URL을 필수로 요구하지만, 링크가 붙어 있다는 사실만으로는 아무것도 보장하지 못합니다. 링크가 주장을 실제로 뒷받침하는지는 별개의 문제입니다.

인용 검증은 두 단계로 나눕니다.

1. **코드**: URL을 가져와 도메인 화이트리스트를 대조하고 본문을 발췌합니다. 도달 불가하거나 본문이 없으면 모델을 부르지 않고 `미검증 출처`로 확정합니다.
2. **판단**: 발췌된 본문과 주장의 관계를 묻습니다.

```python
"evidence_relation": Choice(
    instructions="`evidence.excerpt`의 내용은 `card.evidence_source`의 주장과 어떤 관계인가?",
    criteria={
        "supports": "발췌문이 주장의 근거가 된다",
        "contradicts": "발췌문이 주장과 반대되는 내용을 담고 있다",
        "unrelated": "발췌문이 주장을 다루지 않는다",
    },
)
```

`contradicts`는 단순한 미검증보다 무겁게 다룹니다. 반대 내용을 근거로 제시하는 것은 `04_REPUTATION_MODERATION.md`의 "허위 출처 링크 게시"(-40점)에 해당할 수 있으므로, 높은 확신도에서만 적용하고 그 외에는 사람 검토로 보냅니다.

### 3.4 안건 등록 시

| ID | 유형 | 판단 |
|-|-|-|
| `title_is_neutral` | Noul | 제목이 찬반 어느 쪽으로도 유도하지 않는가 (`00_PRODUCT_SPEC.md` §6) |
| `is_duplicate_of` | Choice | 기존 유사 안건 후보 중 실질적으로 같은 안건은 무엇인가 (`none` 포함) |

중복 판정은 **후보를 코드가 임베딩 유사도로 먼저 추리고, 그중 하나를 모델이 고르는** 구조입니다. 모델에게 전체 안건 목록을 검색시키지 않습니다. 후보에 없는 값은 선택될 수 없으므로, 후보 생성 범위가 곧 판정의 상한입니다.

`none` 선택지를 반드시 포함합니다. 넣지 않으면 모델은 항상 무언가를 고르게 되고, 모든 신규 안건이 중복으로 막힙니다.

### 3.5 대정부 브리프의 합의 문장

**여기서 모델은 문장을 쓰지 않습니다.** 브리프는 국가기관으로 발송되는 공문서이므로, 없던 문장을 생성하면 시민이 쓰지 않은 말이 시민의 합의로 둔갑합니다.

따라서 **선택만 합니다.** 합의 조건을 통과한 실제 카드들을 코드가 모으고, 그중 어느 것이 합의 지점을 가장 정확히 대표하는지 고릅니다. 브리프에는 선택된 **원문이 그대로** 실리고 `ceramic://` 링크가 병기됩니다.

## 4. 무엇을 바꾸지 않는가

TypeSafe로 옮기지 않는 것을 명시합니다.

| 유지 | 이유 |
|-|-|
| **Step 1 온디바이스 스크리닝 (KcELECTRA)** | 타이핑 중 텍스트를 단말 밖으로 내보내지 않기 위한 설계다(`05_CLIENT_APPS.md` §2.4). 이 게이트가 사라지면 프라이버시 설계가 무너진다 |
| **kor_unsmile 멀티라벨 분류** | 한국어 정치 커뮤니티의 신조어·초성 비하에 특화되어 있다. 범용 모델이 이 영역에서 더 낫다는 근거가 없다 |
| **브리징 행렬 분해 · Pol.is** | 수치 계산이다. 의미 판단이 아니므로 모델이 개입할 이유가 없고, 개입하면 G-DETERM이 깨진다 |
| **순화문 생성 (EEVE)** | 생성 작업이다. 판단 모델은 텍스트를 만들지 않는다 |

즉 TypeSafe는 기존 분류기를 대체하는 것이 아니라, **분류기가 할 수 없던 의미 판단을 맡습니다.** "욕설이 있는가"는 kor_unsmile이, "이 비판이 정책을 향하는가 사람을 향하는가"는 판단 모델이 답합니다.

## 5. 감사 가능성 — 이 설계의 가장 큰 이득

`04_REPUTATION_MODERATION.md` §3.2의 공개 중재 로그를 다음과 같이 확장합니다.

```json
{
  "target": "ceramic://k2t6wz...",
  "action": "COACH",
  "judgments": {
    "attack_target": { "choice": "person_or_party",
                       "probabilities": { "policy_substance": 0.11, "person_or_party": 0.78,
                                          "both": 0.09, "neither": 0.02 },
                       "confidence": 0.74 },
    "is_personal_attack": { "noul": 0.81 },
    "norm_severity": { "score": 2.3, "confidence": 0.66 }
  },
  "policy": { "attack_review": 0.35, "attack_action": 0.70, "severity_block": 2.0 },
  "model": "jev-1.13.0",
  "decided_at": "2026-09-21T11:00:00+09:00"
}
```

이 로그가 있으면 누구나 세 가지를 검증할 수 있습니다.

1. **정책 적용이 일관적인가** — 기록된 판단값에 기록된 정책을 다시 적용해 같은 결정이 나오는지 재계산한다. 코드 한 줄이면 된다.
2. **진영별 편향이 있는가** — 찬성 측 카드와 반대 측 카드의 `attack_target` 분포를 비교한다. 한쪽만 체계적으로 높게 나오면 모델 또는 정책에 편향이 있다.
3. **임계치가 자의적으로 바뀌었는가** — 정책값이 로그에 박혀 있으므로 조용한 조정이 드러난다.

기존 설계의 `"reason": "HATE_SPEECH"` 한 줄로는 이 중 어느 것도 할 수 없었습니다.

## 6. 채택 전 해소해야 할 충돌 두 가지

**이 설계는 아래 두 문제가 해결되기 전에는 채택하지 않습니다.** 둘 다 이 프로젝트의 근간에 닿아 있습니다.

### 6.1 제3자 API와 탈중앙 원칙

`ref_docs/project_definition.md:2`는 "중앙서버에서 데이터를 누구도 점령할 수 없도록"을 요구하고, `01_ARCHITECTURE.md` §1.1은 연산 계층이 중앙 통제가 되지 않는 조건을 규정합니다. 그런데 TypeSafe는 상용 호스팅 API입니다.

* 시민이 쓴 **정치적 의견 본문이 제3자 서버로 전송**됩니다.
* 서비스가 중단되거나 정책을 바꾸면 톤 코칭이 멈춥니다.
* 특정 국가의 사업자에게 한국 정치 담론이 축적됩니다.

완화 요소는 있습니다. 온디바이스 0.30 게이트를 통과한 소수의 글만 전송되고, 전송 시점은 타이핑 중이 아니라 제출 후이며, 작성자 신원(DID·필명)은 함께 보내지 않습니다. 그러나 **본문 자체가 나간다는 사실은 남습니다.**

선택지는 셋입니다. ① 채택하고 가입 화면과 개인정보 처리방침에 명시적으로 고지한다. ② 판단 모델을 자체 호스팅한다(보정 품질을 잃고 운영 부담이 늘어난다). ③ 채택하지 않고 기존 분류기만 쓴다(인물·정책 분리 판단을 포기한다).

### 6.2 G-DETERM과 호스팅 모델

`09_DEVELOPMENT_PLAN.md`의 G-DETERM 게이트는 연산 계층 산출물이 **제3자에 의해 재계산 가능**할 것을 요구합니다. 호스팅 모델은 이를 만족할 수 없습니다. `jev-1.13.0`을 고정 재현할 수 없고, 같은 입력에 같은 출력이 보장되지 않습니다.

그런데 톤 코칭 결과는 `wasRevisionRejected`를 통해 **디랭킹(F3)과 평판 차감(-30점)에 영향을 줍니다.** 즉 랭킹에 관여합니다.

현실적 절충은 **재현(reproducibility)을 감사(auditability)로 낮추는 것**입니다. 판단을 재계산할 수는 없지만, §5처럼 전체 판단값·정책·모델 버전을 기록하면 결정의 일관성과 편향은 검증할 수 있습니다. 이 완화를 받아들일지는 제품 결정이며, 받아들인다면 `09_DEVELOPMENT_PLAN.md`의 G-DETERM 정의에 "호스팅 판단 모델은 감사 로그로 대체한다"는 예외를 명시해야 합니다.

## 6.5 기존 방식과의 정면 비교

"TypeSafe로 만들면 안전하고 완벽한가"에 대한 답은 **아니오**입니다. 한 축에서 분명히 낫고 다른 축에서 분명히 나쁩니다. 축을 나눠 봅니다.

### 확실히 나아지는 것

| 항목 | 기존 (프롬프트+JSON 파싱) | 판단 모델 |
|-|-|-|
| **점수의 의미** | 생성 모델이 자기 글을 스스로 채점한다. `0.82`에 확률적 의미가 없어 임계치를 걸 근거가 없다 | 보정된 확률을 돌려준다. 임계치가 통계적 의미를 갖는다 |
| **파싱 실패** | JSON을 벗어나면 판정 불능. 조용한 통과 또는 조용한 차단이 되며 둘 다 사고다 | 정의한 선택지 밖의 값이 나올 수 없다. 실패 모드가 사라진다 |
| **인물·정책 분리** | **구현 수단이 없다.** kor_unsmile은 유해성 분류기이지 비판 대상 분류기가 아니다. 명세가 요구했지만 설계에 구멍이 있었다 | Choice 질문 하나로 해결된다 |
| **임계치 조정** | 프롬프트를 고치고 전량 재추론 | 판단값을 보관하므로 정책만 바꿔 재계산 |
| **편향 감사** | `reason: HATE_SPEECH` 한 줄. 진영별 편향을 검증할 수 없다 | 판단값 분포를 진영별로 비교할 수 있다 |

가장 큰 발견은 세 번째 줄입니다. 기존 설계는 "인물 비방과 정책 비판을 분리한다"고 써 놓고 그 일을 할 수 있는 컴포넌트를 배치하지 않았습니다.

### 확실히 나빠지는 것

| 항목 | 기존 (자체 호스팅) | 상용 API |
|-|-|-|
| **탈중앙 원칙** | 모델 가중치를 직접 보유. 누구에게도 종속되지 않는다 | 시민의 정치적 발언이 해외 상용 서버로 나간다. `ref_docs/project_definition.md:2`의 근간과 충돌 |
| **재현성 (G-DETERM)** | 가중치·시드 고정으로 제3자 재계산 가능 | 모델 버전을 고정할 수 없다. 랭킹에 관여하는 판단이 재현 불가가 된다 |
| **가용성** | 우리가 죽지 않는 한 산다 | 서비스가 멈추면 톤 코칭이 멈춘다 |
| **비용** | 고정비(GPU) | 참여자 수에 비례하는 변동비. 수익 모델이 없는 공익 플랫폼에 불리 |
| **한국어 정치 도메인** | KcELECTRA·kor_unsmile은 초성 비하·은어·신조어로 학습됨 | 범용 모델. `ㅂㅅ` 같은 초성 비하나 한국 정치 은어 성능이 **미검증** |

### 이 프로젝트에서만 특별히 무거운 위험

일반적인 SaaS라면 위 단점은 감수할 만합니다. 그러나 이 플랫폼에서는 하나가 유독 무겁습니다.

**판단 모델에 정치적 편향이 있으면 플랫폼의 존재 이유가 무너집니다.** 진영 편향을 제거하려고 만든 시스템이, 편향을 검증할 수 없는 외부 모델에게 "이 비판이 정당한가"를 묻게 됩니다. 그 모델이 한국 정치 지형에서 어느 쪽 어법에 더 민감한지 우리는 알 수 없고, 가중치를 볼 수 없으므로 고칠 수도 없습니다.

### 권고 — 벤더가 아니라 설계를 가져온다

두 선택지의 이분법이 아닙니다. **가치 있는 것은 TypeSafe의 서비스가 아니라 그 설계 패턴입니다.**

* 타입이 고정된 좁은 판단으로 분해한다
* 판단과 정책을 분리하고 정책은 순수 함수로 둔다
* 원시 판단값을 감사 로그에 남긴다
* 독립 질문은 한 번에 병렬로 묻는다

이 네 가지는 **자체 호스팅으로도 전부 구현 가능합니다.** vLLM의 제약 디코딩(guided decoding)으로 선택지 밖 출력을 원천 차단하고, 선택지 토큰의 확률 분포를 받아 쓰면 됩니다. 다만 **보정(calibration)은 공짜가 아닙니다.** 상용 모델은 보정을 학습했다고 주장하지만, 자체 호스팅에서는 우리가 라벨링한 평가셋으로 온도 보정을 직접 해야 합니다. 이 비용이 §7 검증 계획에 이미 들어 있습니다.

따라서 권고는 다음과 같습니다.

1. **본 문서의 판단 구조·정책 분리·감사 로그는 채택한다.** 벤더와 무관하게 기존 설계보다 낫다.
2. **판단 실행자는 교체 가능한 어댑터 뒤에 둔다.** `services/moderation`을 상용 API와 자체 호스팅 양쪽으로 구현할 수 있게 인터페이스를 고정한다.
3. **상용 API는 평가 단계에서만 쓴다.** §7의 평가셋으로 두 구현을 같은 기준으로 측정하고, 자체 호스팅이 충분하면 그쪽으로 간다.
4. **운영 투입은 §6.1·§6.2가 해소된 뒤에 결정한다.**

즉 지금 단계에서 상용 API를 쓰는 것은 **설계 검증 도구로서**는 합리적이고, **운영 의존 대상으로서**는 아직 정당화되지 않았습니다.

## 7. 검증 계획

채택하기로 결정하더라도 **한국 정치 담론에서의 성능을 먼저 측정해야 합니다.** 문서와 쿡북의 임계치(0.35 / 0.70 / 2.0)는 예시일 뿐, 우리 데이터에서 평가한 값이 아닙니다.

1. 한국어 정치 게시물 300건에 사람이 `attack_target`·`norm_severity`를 라벨링한 평가셋을 만든다.
2. 판단 모델 결과와 대조해 혼동행렬과 보정 곡선을 본다.
3. **진영별로 성능을 나눠 본다.** 한쪽 진영의 어법에서만 오탐이 높으면 그 자체가 정치적 편향이며, 이 플랫폼에서는 치명적이다.
4. 임계치를 우리 데이터에서 다시 정한다.
5. 회색지대(기록만) 구간의 글을 표본 검수해 경고 누락과 과잉 경고의 비율을 확인한다.

3번이 특히 중요합니다. 이 검증을 건너뛰면, 진영 편향을 없애려고 만든 시스템이 편향된 모델로 진영을 판정하게 됩니다.
