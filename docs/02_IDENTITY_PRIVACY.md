# 02. 신원 체계 및 프라이버시 불변식

## 1. 확정된 신원 모델: 검증된 익명

기존 문서는 "등록자명·이메일 공개"(원본 요구)와 "실명·이메일 폐기"(아키텍처)를 동시에 요구해 정면 충돌했습니다. **하이브리드로 확정**했습니다(→ D1).

> **ZK-Email로 1인 1계정만 수학적으로 검증하고, 공개되는 신원은 변경 불가 필명 하나뿐이다. 실명과 이메일은 시스템이 보관하지 않는다.**

### 1.1 원본 요구를 어떻게 충족하는가

원본 요구의 진짜 목적은 "실명 노출" 자체가 아니라 **책임성**이었습니다. 이는 필명으로도 달성됩니다.

| 원본 요구 | 충족 방식 |
|-|-|
| 실명+이메일 인증 후 가입 | ZK-Email이 실제 이메일 소유를 수학적으로 증명. 인증 강도는 오히려 더 높음 |
| 회원 ID는 이메일로 Unique | `Nullifier = Poseidon(Email, AppSalt)`가 이메일당 정확히 하나. 온체인 유일성 강제 |
| 등록자 식별 공개 | 변경 불가 필명 + 인증 배지를 카드마다 표시. 이력이 영구 누적되어 책임 회피 불가 |
| 정치 성향 절대 비노출 | 실명이 없으므로 외부 정보와 결합한 성향 추론 자체가 불가능 |

동시에 실명 공개가 초래했을 문제를 원천 차단합니다. 신상털기, 직장 불이익, 진영 낙인, 그리고 무엇보다 **연구용 오픈 데이터를 공개하는 순간 발생할 개인정보 유출**이 성립하지 않습니다.

### 1.2 필명 체계

* 형식: 사용자 선택 닉네임 + 시스템 부여 4자리 식별자. 예) `광화문산책자#4821`
* **가입 시 1회 결정되며 이후 변경 불가**입니다. 변경을 허용하면 평판 이력을 세탁할 수 있습니다.
* 닉네임에 실명·소속·연락처로 보이는 문자열이 포함되면 등록을 거부합니다.
* 식별자 4자리는 Nullifier에서 결정론적으로 파생하되, Nullifier를 역산할 수 없습니다.

## 2. ZK-Email 가입 파이프라인

```
1. 사용자가 본인 이메일로 CivicAgora 인증 메일 수신
      (정부·포털·대학 등 허용 도메인 화이트리스트)
                    │
2. 클라이언트가 메일 원문을 로컬에서 읽고 DKIM RSA 서명 검증
      Circom 회로 · rapidsnark 네이티브 증명 생성
                    │
3. Nullifier Hash = Poseidon(이메일 주소, AppSalt) 산출
                    │
4. 이메일 원문·주소·실명을 메모리에서 소거
      ZK Proof + Nullifier만 남김
                    │
5. 온체인 컨트랙트에 제출
      · Nullifier 중복 검사 → 이미 있으면 거부
      · ZK Proof 검증 → 유효한 이메일 소유자임을 확인
                    │
6. 로컬 Secp256k1 키페어 생성 → DID 발급 → 필명 확정
      개인키는 OS 보안 저장소에 보관 (Windows Hello / Android Keystore)
```

**핵심 성질**: 3단계 이후 시스템 어디에도 이메일이 존재하지 않습니다. 서버가 압수당해도, 운영자가 악의적이어도, 온체인 데이터를 전부 분석해도 어떤 시민이 어떤 이메일을 썼는지 알아낼 수 없습니다. 동시에 같은 이메일로는 두 번째 계정을 만들 수 없습니다.

### 2.1 계정 복구

익명성의 대가는 복구 불가입니다. 개인키를 잃으면 평판 이력도 사라집니다.

* 가입 시 **복구 구문(12단어)** 을 반드시 백업하게 하고, 확인 절차를 통과해야 가입이 완료됩니다.
* 동일 이메일 재인증으로는 복구할 수 없습니다. Nullifier가 이미 소비되었기 때문입니다.
* 다중 기기는 복구 구문으로 키를 가져오는 방식으로 지원합니다.

> 이 트레이드오프는 사용자에게 가입 화면에서 명시적으로 고지해야 합니다.

## 3. 프라이버시 불변식

아래 다섯 가지는 **코드 리뷰와 테스트로 강제되어야 하는 불변식**입니다. 위반하는 변경은 머지할 수 없습니다.

### INV-1. 정치 성향 입력값은 어떤 경로로도 유출되지 않는다

회원은 가입 시 정치 성향·지지 정당을 선택적으로 기록할 수 있습니다(원본 요구). 그러나 이 값은

* 본인 단말에만 암호화 저장되고 서버·P2P·온체인 어디에도 전송되지 않습니다.
* 본인만 열람할 수 있습니다.
* **브리징 알고리즘의 입력으로도 쓰이지 않습니다.** 알고리즘은 자기 신고값이 아니라 반응 패턴에서 잠재 성향 `f_u`를 스스로 추정합니다.
* 랭킹·검색·통계·오픈 API 어디에도 집계조차 반영되지 않습니다.

> 그렇다면 왜 입력받는가? 사용자가 본인의 자기 인식과 알고리즘이 추정한 `f_u`를 대조해볼 수 있게 하는 **개인용 거울** 기능뿐입니다. 이 기능이 부담스럽다면 수집하지 않는 편이 안전하며, 구현 시 재검토 대상입니다.

### INV-2. 개인의 잠재 성향 `f_u`는 외부로 공개되지 않는다

`f_u`는 브리징 계산의 내부 변수입니다.

* 본인에게만, 그것도 좌우 축의 대략적 위치로만 시각화합니다.
* 타인의 `f_u`는 조회할 수 없습니다.
* **연구자용 오픈 API에서 제거되었습니다.** 기존 명세는 의견마다 `user_latent_factor: -0.12`를 노출했는데, 이는 개인 단위 정치 성향의 직접 공개이며 INV-1과 정면 충돌합니다. 카드 단위 편향 `f_i`만 공개합니다(→ D7, `06_GOV_BRIEF_API.md`).

### INV-3. 누가 어떤 반응을 눌렀는지 공개되지 않는다

반응은 집계 수만 표시합니다. "이 카드에 반응한 사람 목록" 같은 화면은 존재하지 않으며 API로도 제공하지 않습니다. 반응자 목록이 공개되면 반응 패턴에서 개인의 성향을 역산할 수 있습니다.

### INV-4. "반대 진영 긍정 반응" 보상은 개별 건으로 정산하지 않는다

평판 규칙상 반대 성향 사용자로부터 💡·🤝를 받으면 가점이 있습니다. 그런데 반응이 달릴 때마다 즉시 가점하면, 작성자는 **점수 변동만 보고 방금 반응한 사람의 진영을 역추론**할 수 있습니다.

따라서 **일 1회 배치 정산**합니다. 브리징 모델을 재학습한 뒤 그날의 교차 진영 가점을 합산해 한 번에 반영하고, 어떤 반응이 가점 대상이었는지는 밝히지 않습니다.

### INV-5. 집계 공개에는 최소 인원 기준을 적용한다

소수 집단은 집계만으로도 식별될 수 있습니다.

* 클러스터별 찬성률은 해당 클러스터 인원이 **20명 이상**일 때만 표시합니다.
* 오픈 API는 참여자 50명 미만 안건의 데이터를 내보내지 않습니다.
* 시간 정보는 분 단위 이하를 버리고 시간 단위로 반올림합니다. 작성 시각의 정밀도는 작성 패턴을 통한 재식별 경로입니다.
