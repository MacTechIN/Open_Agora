# 08. 검증 기록 및 확정 결정 (ADR)

기존 `docs/` 문서들을 한 줄씩 대조해 검증한 결과(D1–D14)와, 이후 구현하면서 나온 결정(D15–D22)입니다. **총 22건** — 이 중 D19는 확정이 아니라 임시 결정입니다.

D1–D14는 문서 대조에서, D15–D22는 구현에서 나왔습니다. 후자는 만들어 보기 전에는 보이지 않던 것들입니다 — 예컨대 D16(찬반은 주제가 아니라 쟁점 질문에 대한 것)은 화면을 만들어 놓고 써 보니 답할 수 없는 질문이 나와서 알았습니다.

각 항목은 **증거(파일:줄) → 충돌 내용 → 확정 → 근거** 순서로 기록합니다. 나중에 결정을 뒤집으려 할 때 무엇을 다시 검토해야 하는지 알 수 있도록 근거를 남깁니다.

## D1. 신원 모델 — 실명 공개 vs 완전 익명

**증거**
* `ref_docs/project_definition.md:3` — "실명+본인이메일로 인증 후 회원 가입"
* `ref_docs/project_definition.md:10` — "회원 ID는 이메일 주소로 Unique"
* `ref_docs/project_definition.md:13` — "등록 글은 등록자명, 아이디(이메일)이 공개되고"
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:57` — "실제 이메일과 사용자 이름은 폐기되며"
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:59` — "`Citizen_XXXX` 고유 식별자 발급"

**충돌** 원본 요구는 실명과 이메일의 **공개**를, 아키텍처는 **폐기**를 규정합니다. 양립 불가능하며 신원 레이어 전체 설계를 좌우합니다.

**확정** **하이브리드 — 검증된 익명.** ZK-Email로 1인 1계정만 수학적으로 검증하고, 공개되는 것은 변경 불가 필명 + 인증 배지뿐입니다. 실명·이메일은 시스템이 보관하지 않습니다.

**근거** 원본 요구의 목적은 실명 노출 자체가 아니라 **책임성**이며, 변경 불가 필명에 이력이 영구 누적되면 동일하게 달성됩니다. 결정적으로 `ref_docs/project_definition.md:12`가 "정치적 성향은 절대 노출되어서는 안 된다"를 요구하는데, 실명이 공개되면 작성 이력과 외부 정보를 결합해 성향을 추론할 수 있어 **원본 문서가 자기 자신과 모순**됩니다. 또한 `ref_docs/project_definition.md:14`의 연구용 오픈 데이터 공개는 실명 체계에서는 개인정보 유출이 되어 실행 불가능합니다. → `02_IDENTITY_PRIVACY.md`

## D2. 토론 구조 — 2분할 vs 3축

**증거**
* `ref_docs/project_definition.md:13` — "찬성/반대의 두 가지 항목에서 글이 등록되고 좌우에 분리되어"
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:79` — `stance: StanceType! # ENDORSE | CONCERN | ALTERNATIVE`

**충돌** 원본은 좌우 2분할, 스키마는 3개 스탠스입니다.

**확정** **3열 — 찬성(SUPPORT) | 대안·합의(ALTERNATIVE) | 반대(OPPOSE).** 좌우 두 열은 시각적으로 완전히 동등하고, 가운데 열은 브리징 알고리즘의 산출물입니다.

**근거** 두 요구가 실제로는 충돌이 아니었습니다. 원본이 요구한 "좌우 동등 분리"는 좌우 두 열로 그대로 충족되고, `ALTERNATIVE`는 좌우 어디에도 속하지 않는 제3안이므로 가운데 열이 제 자리입니다. 그리고 이 가운데 열은 `ref_docs/algorithms_ai_pipeline_specification.md:47`의 "Common Ground" 다이어그램이 이미 그리고 있던 공간과 정확히 일치합니다. 스탠스 이름은 원본의 찬반 어휘에 맞춰 `ENDORSE`→`SUPPORT`, `CONCERN`→`OPPOSE`로 변경했습니다. → `00_PRODUCT_SPEC.md` §2

## D3. 삭제 정책 — 삭제 가능 vs 영구 보존 vs 불변성

**증거**
* `ref_docs/project_definition.md:10` — "AI에 의해 욕설비방음란적이나 사회적으로 문제가 되지 않는 이상 지워지지 않고 영원히 검색이 가능"
* `ref_docs/project_definition.md:2` — "누구도 데이터를 왜곡하거나 지울 수 없고"
* `ref_docs/03_SERVICE_SPEC_AND_API.md` §2 — 순화 거부 시 "상단 노출 디랭킹"

**충돌** 3자 충돌입니다. AI가 문제 글을 삭제할 수 있어야 하고, 동시에 영원히 보존되어야 하며, 동시에 누구도 지울 수 없어야 합니다.

**확정** **삭제 기능 없음.** 디랭킹 → 블라인드 → 검색 제외 3단계 노출 조정만 존재합니다. 작성자 본인도 삭제할 수 없습니다.

**근거** 블라인드는 UI 계층의 표시 규칙일 뿐이고 IPFS 원문과 온체인 앵커는 유지되므로, "지울 수 없다"와 "유해 글이 노출되지 않는다"를 동시에 만족합니다. 삭제 권한을 가진 주체를 만드는 순간 탈중앙 원칙이 무너집니다. 남용을 막기 위해 모든 노출 조정 이력을 공개 로그로 남기고, 최종 단계는 성향 균형을 맞춘 시민 배심이 판정합니다. → `04_REPUTATION_MODERATION.md` §3

## D4. 반응 아이콘 세트

**증거**
* `ref_docs/project_definition.md:13` — "좋아요, 반대해요, 별로에요, 추천해요"
* `ref_docs/03_SERVICE_SPEC_AND_API.md:20` — "논리적이에요(💡) 또는 공감해요(🤝)"
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:26` — "상호 반응(💡, 🤝, 🔍, ⚖️)"
* `ref_docs/03_SERVICE_SPEC_AND_API.md` §4 — API 필드 `logical` / `empathy` / `needs_factcheck` / `suggests_alternative`

**충돌** 세 가지 다른 세트가 존재합니다.

**확정** **긍정 2 + 부정 2** — 💡논리적이에요 · 🤝공감해요 (`r=1`) / 🔍팩트체크 필요해요 · ⚖️이견 있어요 (`r=0`). 카카오톡 이모지처럼 표시하고 집계 수를 노출합니다.

**근거** 브리징 행렬 분해는 이진 신호 `r ∈ {0,1}`를 요구하므로 부정 반응이 반드시 필요합니다. 그런데 기존 4종(💡🤝🔍⚖️)은 명확한 부정이 없었고, 원본 4종은 "좋아요 vs 추천해요", "반대해요 vs 별로에요"가 의미상 중복되어 신호 품질을 떨어뜨렸습니다. 양쪽의 결함을 각각 보완해 재구성했습니다. API 필드명 `suggests_alternative`는 부정 신호를 나타내도록 `disagree`로 변경했습니다. → `00_PRODUCT_SPEC.md` §5

## D5. 합의 임계치 — 0.65 vs 0.60

**증거**
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:227` — `Agreement(A) ≥ 0.65 ∧ Agreement(B) ≥ 0.65`
* `ref_docs/algorithms_ai_pipeline_specification.md:54` — `Consensus(i) ≥ 0.60`
* `ref_docs/03_SERVICE_SPEC_AND_API.md` §3 — 브리프 예시 "지지도 84.1%, 양 진영 지지율 격차 3.2% 이내"

**충돌** 같은 판정에 대해 0.65와 0.60이 병존합니다.

**확정** **충돌이 아니라 두 개의 관문으로 정합화.**
* 1차 — 합의 배너 승격: 모든 군집 ≥ **0.60**
* 2차 — 대정부 브리프 수록: 모든 군집 ≥ **0.65** 이며 군집 간 격차 ≤ **5%p**

**근거** 플랫폼 내부 노출과 국가기관 공문 발송은 요구되는 확신의 수준이 다릅니다. 이 해석은 기존 브리프 예시가 이미 "격차" 기준을 별도로 언급하고 있다는 점과 정확히 부합하며, 두 수치를 모두 살리면서 각각에 명확한 역할을 부여합니다. → `03_ALGORITHMS_AI.md` §2.2

## D6. 톤 코칭 파이프라인 — 모델 순서와 임계치

**증거**
* `ref_docs/01_SYSTEM_ARCHITECTURE.md:247-251` — Step 1이 Kor-Unsmile, 임계치 0.3
* `ref_docs/algorithms_ai_pipeline_specification.md:70-78` — Step 1이 KcELECTRA, Step 2가 KorUnsmile, 임계치 0.65

**충돌** 1차 모델이 무엇인지, 임계치가 얼마인지 모두 다릅니다.

**확정**
* 순서: **KcELECTRA-base-v2022 (고속) → kor_unsmile (정밀 멀티라벨) → EEVE (순화문 생성)**
* 임계치: **0.30 = 1차 통과 게이트**, **0.65 = 2차 배너 트리거**. 0.30~0.65는 경고 없이 통과시키되 기록하는 회색지대.

**근거** 순서는 성능 제약으로 결정됩니다. 멀티라벨 분류기를 모든 타이핑마다 실행할 수 없으므로 가벼운 모델이 먼저 걸러야 하며, 따라서 `01` 문서의 역순은 오류입니다. 임계치는 D5와 같은 구조로, 두 숫자가 파이프라인의 서로 다른 지점을 가리키는 것으로 해석하면 모순 없이 양립합니다. 회색지대를 둔 이유는 무해한 강한 어조까지 경고하면 코치가 잔소리가 되어 사용자가 이탈하기 때문입니다. → `03_ALGORITHMS_AI.md` §3

## D7. 프라이버시 — 성향 비노출 vs 성향 기반 기능

**증거**
* `ref_docs/project_definition.md:12` — "정치적 성향, 정당명 … 절대 노출이 되어서는 안 된다"
* `ref_docs/03_SERVICE_SPEC_AND_API.md:20` — "반대 진영 사용자로부터 … 획득 시 +5점 / 건"
* `ref_docs/03_SERVICE_SPEC_AND_API.md` §4 — API 응답 필드 `"user_latent_factor": -0.12`

**충돌** 성향을 절대 노출하지 말라면서, 성향에 기반한 즉시 가점과 개인 단위 성향값 공개 API를 동시에 규정합니다.

**확정** 세 가지 조치를 적용합니다.
1. **오픈 API에서 `user_latent_factor` 제거.** 카드 단위 편향 `opinion_bias_factor`($f_i$)로 대체.
2. **교차 진영 가점은 일 1회 배치 정산.** 건별 즉시 반영 금지.
3. 사용자가 입력한 성향값은 **단말에만 암호화 저장**하고 알고리즘 입력으로도 쓰지 않음.

**근거** `user_latent_factor`는 의견마다 작성자 개인의 정치 성향 좌표를 그대로 공개하는 값으로, 여러 안건을 결합하면 개인을 재식별할 수 있습니다. 가점을 건별로 즉시 반영하면 작성자가 **점수 변동만 보고 방금 반응한 사람의 진영을 역추론**할 수 있으므로 배치 정산이 필요합니다. 연구 목적에 필요한 정보는 $f_i$로 충분히 제공됩니다. → `02_IDENTITY_PRIVACY.md` §3, `06_GOV_BRIEF_API.md` §2.3

## D8. 근거 URL — 선택 vs 필수

## D15. 기기 키 곡선 — secp256k1 vs P-256

**증거**
* `ref_docs/01_SYSTEM_ARCHITECTURE.md` — "로컬 키페어 (Secp256k1 DID)"
* `09_DEVELOPMENT_PLAN.md` VS-A2 수용 기준 — "개인키가 Android Keystore / Windows Hello에 저장되고 앱 메모리로 평문 노출되지 않음"
* Android 문서 — StrongBox KeyMint 지원 목록은 **RSA 2048, AES, ECDSA·ECDH P-256, HMAC-SHA256, 3DES**. secp256k1은 없다

**충돌** 두 요구가 Android에서 양립하지 않는다. secp256k1을 쓰면 하드웨어 보호를 포기하고 소프트웨어 키로 내려와야 하며, 그러면 개인키가 앱 메모리에 올라온다.

**확정** **P-256(secp256r1)** 을 기기 키 곡선으로 쓴다. DID는 `did:key`로 표현한다.

**근거** 우선순위는 하드웨어 보호입니다. 개인키가 메모리에 오르면 코어 덤프, 디버거, 루팅된 기기에서 탈취될 수 있고, 이 플랫폼에서 키 탈취는 곧 시민 신원 도용입니다. 반면 secp256k1을 포기해 잃는 것은 크지 않습니다.

* Ceramic은 `did:key`와 `did:pkh`를 모두 지원하며 `did:key`는 P-256을 포함한다
* Semaphore 신원 커밋먼트는 Poseidon 기반 비밀에서 파생되며 EC 키가 아니다
* 온체인 제출이 필요한 지점은 릴레이어로 처리할 수 있어 기기 키가 이더리움 계정일 필요가 없다

**구현 제약** 코어는 개인키를 다루지 않습니다. 키 생성과 서명은 플랫폼(Android Keystore / Windows CNG)이 수행하고, 코어는 공개키를 받아 DID를 만들고 서명을 검증하기만 합니다. **코어에 개인키를 다루는 함수를 만들지 않는 것 자체가 설계**입니다. → `core/src/identity.rs`, `docs/09_DEVELOPMENT_PLAN.md` VS-A2

## D18. 대정부 전달 방식 — 플랫폼 발송에서 회원 다운로드로

**기존** 플랫폼이 "발신: CivicAgora 시민 공론장 거버넌스"로 국회·부처에 공문을 직접 발송(`06_GOV_BRIEF_API.md` §1.4).

**근거**

1. **대표성 논란을 피합니다.** 플랫폼이 "시민 합의"를 대표해 발송하면 "누가 시민을 대표하는가"라는 물음에 답해야 합니다. 회원이 각자 쓰면 그 물음이 성립하지 않습니다.

4. **운영 부담이 사라집니다.** 기관별 양식과 수신처 관리가 필요 없습니다.

**함께 바뀌는 것**: 발행 조건을 1,000건·500명에서 **100건·50명**으로 낮춥니다. 기존 기준은 초기 플랫폼에서 도달 불가능해 기능이 작동하지 않습니다. 대신 보고서에 표본 규모를 명시해 읽는 사람이 무게를 판단하게 합니다.

**유지되는 것**: 합의에 이르지 못한 쟁점을 함께 싣는 것, 검증 정보(온체인 앵커·재계산 방법·모델 버전)를 포함하는 것. 이 둘이 없으면 선전물이 되거나 신뢰할 근거가 없어집니다. → `14_USER_JOURNEY.md` §3, §4

## D20. 앵커링 수단 — EVM L2 에서 OpenTimestamps 로 (2026-09-22)

**기존** `16_ONCHAIN_PLAN.md` 2단계는 Arbitrum One 또는 Base 에 6시간마다 머클 루트를 기록하고 월 수천 원을 쓰는 계획이었습니다.

**확정** **OpenTimestamps(비트코인)로 시작합니다.** EVM 앵커링은 폐기하지 않고 나중에 더할 수 있게 자리를 비워 둡니다(`anchor_batches.chain_tx`).

**근거**

1. **EVM 경로는 지금 막혀 있습니다.** L2 체인이 아직 선정되지 않았고(미결 사항), 지갑과 가스비가 필요합니다. 쓸 수 없는 경로를 만들어 두는 것보다 도는 것을 만드는 편이 낫습니다.
2. **지갑도 개인키도 필요 없습니다.** 해시만 보냅니다. 운영자가 지갑을 관리해야 한다면 그 지갑이 새 단일 실패 지점이 됩니다.
3. **비용이 0원입니다.** 월 수천 원도 적지만, 0원은 "요금이 밀려 앵커링이 멈췄다"는 상태가 아예 생기지 않는다는 뜻입니다.
4. **영수증이 표준 `.ots` 파일입니다.** 공식 도구(`ots verify`)로 검증됩니다. **우리 코드를 믿지 않아도 됩니다** — 이것이 결정적입니다. 자체 컨트랙트를 쓰면 검증자가 우리 ABI와 우리 설명을 먼저 믿어야 합니다.
5. 사용자의 방침과 맞습니다 — "블록체인은 이미 사용 중인 서비스를 쓰면 된다"(D-이전 지시).

**맞바꾼 것**

* **확정까지 몇 시간** 걸립니다. 비트코인 블록에 들어가야 하고, 그 전까지 영수증은 `Pending` 입니다. L2 는 몇 초입니다. 앵커링의 목적이 *소급 조작 탐지*이므로 몇 시간의 지연은 문제가 되지 않습니다.
* **스마트 컨트랙트 연동이 없습니다.** 평판 SBT(D13)나 Semaphore 와 같은 체인에 두는 이점은 포기합니다. 그것들은 각자 자기 체인을 고르면 됩니다.

**바뀌지 않는 것**: 머클 트리 형식, 잎 정의, 증명 API. 나중에 EVM 을 더해도 같은 루트를 올립니다.

## D21. 한 이메일에 여러 기기 (2026-09-22)

**기존** 한 이메일로 **한 DID** 만 등록. 두 번째 인증은 "이미 가입한 이메일입니다"로 거절.

**확정** 한 이메일로 **최대 5대의 기기**를 등록합니다. 같은 이메일로 다시 인증하면 거절하지 않고 그 기기를 더합니다.

**무엇이 잘못됐었나**

시민 ID는 기기 안에서 만들어지고 **기기 밖으로 나오지 않습니다**(브라우저 IndexedDB, Windows TPM, Android Keystore, iOS Secure Enclave). 하드웨어 키는 내보낼 수 없으므로 기기마다 반드시 다른 DID가 됩니다.

그런데 "한 이메일 = 한 DID"로 두면 실제로는 **한 이메일 = 한 기기**가 됩니다. 결과는 이렇습니다.

* 웹에서 가입한 사람이 Windows 앱을 열면 다른 DID라 글을 쓸 수 없고, 등록하려 해도 이메일이 소진되어 거절됩니다
* 브라우저 데이터를 지우면 **영구히 잠깁니다**

사람과 기기를 같은 것으로 취급한 설계 오류였습니다. 사용자가 "한번 시민등록 한 회원은 어떻게 내 아이디로 등록하지?"라고 물어 드러났습니다.

**대안을 고른 이유**

| 대안 | 문제 |
|-|-|
| 복구 구문으로 키 복원 (VS-C4) | 하드웨어 키는 복원할 수 없습니다. 소프트웨어 키로 내려가면 네이티브 앱의 보호를 잃습니다 |
| 기존 기기로 새 기기에 서명(pairing) | 기기를 잃으면 못 씁니다. 잠김 문제가 그대로 남습니다 |
| **이메일 재인증으로 기기 추가** | 채택. 기기를 다 잃어도 이메일만 있으면 됩니다 |

**프라이버시에 미치는 영향**: 없습니다. `consumed_emails`에 기기 수(정수)만 더했고 **어떤 DID인지는 담지 않습니다.** 두 표는 여전히 연결 키가 없습니다.

**약해진 것**: 한 사람이 최대 5개의 DID를 갖습니다. 지금은 반응·투표가 없어 피해가 없지만, **VS-D2(반응 4종) 전에 1인 1표를 다른 수단으로 보장해야 합니다.** 그것이 VS-C3(Semaphore nullifier)입니다. 상한 5는 무한정 늘리는 것을 막는 약한 방어일 뿐, 1인 1표의 보장이 아닙니다.

**연결**: `02_IDENTITY_PRIVACY.md`, `09_DEVELOPMENT_PLAN.md` VS-C3·VS-C4

## D22. 익명 회원권을 체인 없이 먼저 (VS-C3a, 2026-09-23)

**기존** VS-C3(가입 플로우 전체)는 ZK-Email 증명 → 온체인 Nullifier 컨트랙트 → 필명 확정을 한 슬라이스로 묶었습니다. 선행은 VS-C1(증명 생성)과 VS-C2(컨트랙트)입니다.

**확정** VS-C3를 둘로 나눕니다.

| | 내용 | 상태 |
|-|-|-|
| **VS-C3a** | Semaphore 익명 회원권 + 1인 1표. 그룹은 오프체인, 루트는 앵커링 | **완료** |
| **VS-C3b** | ZK-Email로 이메일↔신원 연결 끊기 | 막힘 (C1·C2·체인) |

**근거**

1. **급한 것은 1인 1표입니다.** 한 사람이 기기를 5대까지 등록할 수 있어(D21) 반응·투표를 DID로 세면 다섯 몫을 행사합니다. VS-D2 착수 전에 막아야 합니다.
2. **체인이 없어도 됩니다.** Semaphore의 증명 검증은 오프체인에서 됩니다. 온체인이 주는 값어치는 *그룹 루트를 누구나 확인할 수 있다*는 것인데, 그 자리는 앵커링(VS-F6)이 대신합니다 — 그룹 루트를 배치에 실어 비트코인에 남깁니다.
3. **ZK-Email은 아직 막혀 있습니다.** Gmail·네이버·다음·네이트의 DKIM 셀렉터를 확보하지 못했습니다(→ `13_VS_C0_FINDINGS.md` §10).

**신원이 기기가 아니라 사람에 묶입니다**

익명 신원은 **12단어 복구 문구**에서 결정적으로 나옵니다. 같은 문구는 어느 기기에서든 같은 커밋먼트를 만들므로, 기기가 여럿이어도 한 몫만 갖습니다. 시민 ID(did:key)가 기기에 묶이는 것과 정반대이며, 그래야 1인 1표가 성립합니다.

**문구를 잃으면 되찾을 수 없습니다.** 서버가 복구해 줄 수 있다면 서버가 그 사람의 표를 흉내 낼 수 있다는 뜻이므로, 복구 불가는 결함이 아니라 성질입니다. 가입 화면에서 그대로 알리고 확인을 받습니다(VS-C4의 수용 기준을 앞당겨 적용).

**남은 한계 — 정직하게**

* **가입 순간 서버는 이메일과 커밋먼트를 함께 봅니다.** 저장하지 않을 뿐입니다. 이 마지막 연결을 끊는 것이 VS-C3b입니다.
* 네트워크 수준 메타데이터(IP·시각)는 여전히 서버가 봅니다. 증명은 *누구인지*를 감추지 *언제 어디서*를 감추지 않습니다.
* 그룹 명부는 우리가 관리합니다. 가짜 회원을 끼워 넣을 수 있지만, 루트가 앵커에 남으므로 **끼워 넣은 사실이 드러납니다.**

**자체 세리머니는 하지 않습니다.** 2024-07-13에 400명 이상이 참여해 끝난 Semaphore V4 세리머니 결과물을 그대로 씁니다. 아티팩트는 저장소에 고정하고 해시를 대조합니다 — 런타임 다운로드를 두면 CDN이 멈출 때 투표가 전면 중단되고, 바뀐 아티팩트를 받아도 알 수 없습니다.
