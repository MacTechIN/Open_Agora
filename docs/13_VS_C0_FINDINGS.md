## 신규 발견 — DKIM 레지스트리가 새로운 단일 실패점이다

`12_ONCHAIN_DEPENDENCIES.md` §2는 "자체 신뢰 설정을 하지 말라"고 했습니다. 근거는 세리머니 부산물이 남으면 증명을 위조해 **가짜 시민을 무제한 생성**할 수 있고 그것이 탐지 불가능하다는 것이었습니다.

조사 결과, **세리머니를 외부에 맡겨도 같은 능력을 가진 주체가 다른 곳에 생깁니다.**

`zkemail/zk-email-verify`의 `DKIMRegistry.sol`:

```solidity
contract DKIMRegistry is IDKIMRegistry, Ownable {
    constructor(address _signer) Ownable(_signer) {}

    function setDKIMPublicKeyHash(...) public onlyOwner { ... }
    function revokeDKIMPublicKeyHash(bytes32 publicKeyHash) public onlyOwner { ... }
}
```

DKIM 검증은 "이 도메인의 공개키로 서명이 검증되는가"를 확인합니다. 그 **공개키 목록을 소유자가 임의로 바꿀 수 있습니다.** 소유자가 자신이 개인키를 가진 키쌍을 `naver.com`의 DKIM 키로 등록하면, 직접 서명한 가짜 인증 메일이 회로를 통과하고 유효한 증명이 나옵니다. 결과는 세리머니 오염과 동일합니다 — **가짜 시민 무제한 생성, 그리고 탐지 불가.**

즉 §2의 논거는 여전히 옳지만 불완전했습니다. 위험이 사라진 게 아니라 **세리머니 운영자에서 DKIM 레지스트리 소유자로 이동**했을 뿐입니다.

### 완화 수단은 존재한다

같은 저장소가 `UserOverrideableDKIMRegistry.sol`을 제공합니다.

* `mainAuthorizer` — 주 권한자
* `setTimestampDelay` — 주 권한자가 설정한 키 해시가 **활성화되기까지의 시간 지연**
* 사용자 단위 오버라이드 — 개별 사용자가 특정 키 해시를 승인/거부

시간 지연이 핵심입니다. 악의적 키가 등록되어도 즉시 발효되지 않으므로, 감시자가 온체인 이벤트를 관찰해 대응할 시간이 생깁니다. 탐지 불가능한 위험이 **탐지 가능한 위험으로 바뀝니다.**

### 결정

1. **평범한 `DKIMRegistry`를 쓰지 않는다.** 단일 소유자 모델은 이 플랫폼의 전제와 양립하지 않는다.
2. **`UserOverrideableDKIMRegistry`를 채택하고**, `mainAuthorizer`를 다중서명 지갑으로 두며, `setTimestampDelay`를 **최소 7일**로 설정한다.
3. **DKIM 키 변경 이벤트를 공개 감시 대상으로 만든다.** 새 키 해시가 등록되면 플랫폼에 공지하고, 발효 전 이의를 받는다. `11_SOVEREIGN_JUDGMENT.md` §5.1의 모델 교체 거버넌스와 동일한 절차를 적용한다.
4. 이 위험을 `08_DECISIONS.md`에 명시 기록한다. 감출 성격의 사안이 아니다.

> 한국 주요 도메인(naver.com, gmail.com, daum.net, 정부·대학 도메인)의 DKIM 키는 실제로 주기적으로 교체됩니다. 따라서 레지스트리는 **운영 중 계속 갱신되어야 하는 살아 있는 구성요소**이며, 일회성 설정이 아닙니다. 갱신 절차를 운영 문서에 포함해야 합니다.

## 1. Semaphore 신뢰 설정 세리머니 — 🟢 확정 (§7.1에서 해소)

**확인된 것**

Semaphore 문서가 세리머니의 존재를 명시합니다.

> "Generating valid zero-knowledge proofs requires files that can only be obtained in an **attested trusted-setup ceremony**." — `packages/proof/README.md`

> "The secure, verifiable parameters generated by **Semaphore's trusted setup ceremony**. ... During the trusted setup, parameters are specifically generated for each circuit instance, aligning with their designated MAX_DEPTH (from 1 to 32)." — V4 glossary

저장소는 활발합니다(마지막 푸시 2026-09-18).

**확인하지 못한 것**

* 세리머니 참여자 수
* 기여 증명(attestation) 전사본의 공개 위치
* 개별 기여를 독립 검증하는 절차

**주의 사항**: 아티팩트 배포 저장소로 문서가 가리키는 `privacy-scaling-explorations/snark-artifacts`가 **아카이브 상태**(2025-08-26)입니다. Semaphore 본체는 활발하므로 배포처가 이동했을 가능성이 높지만, **런타임에 아티팩트를 자동 다운로드하는 경로에 의존하면 안 됩니다.**

**결정**

* 세리머니 존재는 확인됐으므로 **자체 세리머니를 하지 않는다는 방침은 유지**한다.
* 단, **아티팩트를 런타임에 내려받지 않는다.** 검증한 아티팩트를 저장소에 고정하고 해시를 기록하며, `11_SOVEREIGN_JUDGMENT.md` §5처럼 IPFS에 고정해 CID를 온체인에 앵커링한다. 판단 모델에 적용한 원칙을 증명 아티팩트에도 동일하게 적용한다.
* ~~참여자 수와 전사본 위치 확인~~ → **§7.1에서 해소.** 400명 이상 참여, 2024-07-13 완료, 이더리움 블록 20300394 앵커링.

**영향 범위**

`01_ARCHITECTURE.md` §3이 정의한 데이터 모델 전체가 ComposeDB GraphQL 스키마입니다.

* `Policy`, `DebateCard`, `Reply`, `Reaction` 네 모델
* **`Reaction`의 `accountRelation: SET`** — (작성자, 카드) 유일성을 프로토콜 수준에서 강제하는 장치
* `@documentAccount`, `@documentVersion`, `@string(maxLength:)` 지시자

이 중 `accountRelation: SET`이 특히 중요합니다. `00_PRODUCT_SPEC.md` §5의 "한 사용자는 카드 하나당 반응 하나"를 **애플리케이션 로직이 아니라 데이터 계층이 보장**하도록 설계한 부분입니다. 대체 스택이 같은 보장을 제공하지 못하면 유일성을 직접 구현해야 하고, 그러면 브리징 알고리즘의 입력 무결성이 우리 코드 품질에 걸리게 됩니다.

**결정**

* **VS-B2(Ceramic 영속화)를 착수 전 상태로 되돌린다.**
* 신규 슬라이스 **VS-B2′ (데이터 계층 재선정)** 를 Phase 1에 추가한다.
* 후보: ① Ceramic One + Ceramic SDK로 이전 ② 다른 P2P 문서 저장소 ③ libp2p 위에 자체 CRDT 계층.
* 선정 기준: **서명 검증, 시점 앵커링, (작성자, 대상) 유일성 강제, 부분 복제**. 앞의 셋을 제공하지 못하면 대안이 아니다.
* 결론이 날 때까지 `01_ARCHITECTURE.md` §3 상단에 **잠정 표시**를 단다.

이것이 VS-C0에서 가장 비용이 큰 발견입니다. 다만 **VS-B2에 착수하기 전에 발견한 것이 이 슬라이스의 목적**이었습니다. 구현 후에 알았다면 되돌릴 거리가 훨씬 길었을 것입니다.

## 3. zk-email nullifier 레지스트리 — ⚪ 제공하지 않음

`zkemail/zk-email-verify`의 컨트랙트는 다음이 전부입니다.

```
DKIMRegistry.sol
ECDSAOwnedDKIMRegistry.sol
UserOverrideableDKIMRegistry.sol
```

모두 **DKIM 공개키 레지스트리**이며 nullifier 집합이 아닙니다.

**결정**: `12_ONCHAIN_DEPENDENCIES.md` §4의 자체 nullifier 집합 컨트랙트가 필요하다는 판단을 **확정**합니다. 규모는 그대로 함수 하나입니다.

참고로 zkemail 조직 자체는 매우 활발합니다(다수 저장소가 2026-09-18 푸시). 의존 대상으로서의 지속성 우려는 낮습니다.

## 5. Semaphore 그룹 관리자 모델 — 🟢 우려 해소

`Semaphore.sol` 주석:

> "Group admins can add, update or remove group members, and can be **an Ethereum account or a smart contract**."

```solidity
function createGroup(address admin) external override returns (uint256 groupId)
function addMember(uint256 groupId, uint256 identityCommitment) external
function updateMember(...) external onlyGroupAdmin(groupId)
```

**관리자를 스마트 컨트랙트로 지정할 수 있습니다.** 따라서 §4의 nullifier 컨트랙트를 그룹 관리자로 두면, 사람이나 EOA가 아니라 **"유효한 ZK 증명 + 미사용 nullifier"라는 조건만이 가입을 결정**합니다.

**결정**

* 그룹 관리자는 반드시 우리 nullifier 컨트랙트로 지정한다. EOA를 관리자로 두지 않는다.
* 그 컨트랙트에 **멤버 제거 경로를 만들지 않는다.** 관리자가 제거할 수 있다면 "시민 자격 박탈" 권한이 생기며, 이는 `04_REPUTATION_MODERATION.md`의 삭제 없는 중재 원칙과 어긋난다.
* 컨트랙트를 업그레이드 불가로 배포한다. 업그레이드 권한은 제거 권한과 같다.

### 7.1 Semaphore 세리머니 — 🟢 해소

Semaphore V4 문서가 명확히 답합니다.

> "The secure parameters for generating valid proofs with Semaphore circuits were generated in a Trusted Setup Ceremony that was **completed with over 400 participants on 13 July 2024**."

| 항목 | 값 |
|-|-|
| 참여자 | **400명 이상** |
| 완료일 | 2024-07-13 |
| 온체인 앵커 | 이더리움 블록 [20300394](https://etherscan.io/block/20300394) |
| 세리머니 페이지 | `ceremony.pse.dev/projects/Semaphore V4 Ceremony` |
| 감사 | v2.0.0 PSE 감사 보고서 공개 (`circuits`, `contracts` 범위) |

**판단**: `12_ONCHAIN_DEPENDENCIES.md` §2의 논거가 정량적으로 뒷받침됩니다. 400명 전원이 공모해 부산물을 보관해야 위조가 가능하며, 이는 실무적으로 불가능합니다. 소규모 팀이 자체 세리머니를 운영하는 것과 비교 자체가 되지 않습니다. 완료 사실이 이더리움 블록에 앵커링되어 있어 사후 조작도 불가능합니다.

**자체 세리머니를 하지 않는다는 방침을 확정합니다.**

### 7.2 아티팩트 배포처 — 🟡 조건부

| 항목 | 값 |
|-|-|
| 패키지 | `@zk-kit/artifacts` v2.0.1 (`@semaphore-protocol/proof`의 의존성) |
| 호스팅 | `snark-artifacts.pse.dev` (PSE 운영) — **HTTP 200, 생존 확인** |
| 브라우저 경로 | unpkg URL 직접 사용 |
| 소스 저장소 | `privacy-scaling-explorations/snark-artifacts` — **아카이브(2025-08-26)** |

CDN은 살아 있지만 이를 뒷받침하는 저장소는 동결 상태입니다. 더 중요한 것은 **기본 동작이 런타임 다운로드**라는 점입니다. 가입 경로 한복판에 외부 CDN 의존이 들어가며, CDN이 멈추면 **신규 가입이 전면 중단**됩니다.

**판단**: §1의 결정을 유지·강화합니다. 아티팩트를 저장소에 고정하고 해시를 기록하며, IPFS에 고정해 CID를 온체인에 앵커링합니다. **런타임 다운로드 경로를 코드에서 제거합니다.** 판단 모델 가중치(`11_SOVEREIGN_JUDGMENT.md` §5)와 동일하게 취급합니다.

### 7.3 Ceramic One의 유일성 강제 — 🟢 해소

§2에서 가장 우려했던 부분입니다. `accountRelation: SET`이 사라지면 반응 유일성을 우리가 직접 구현해야 하고, 그러면 브리징 입력 무결성이 우리 코드 품질에 걸립니다.

**Ceramic One에 그대로 보존되어 있습니다.**

> "A model that defines a `set` accountRelation ensures that each Ceramic user can create a unique set of model instance documents based on the corresponding **field(s) that define the set constraint** in the schema. For example, a marketplace application might want to allow users to leave reviews for products they've purchased, and would want to ensure that **each user can only leave 1 review per product**."

문서의 예시가 우리 `Reaction`과 정확히 같은 구조입니다.

```typescript
// Ceramic One ModelDefinition (v2.0)
const reactionModel: ModelDefinition = {
  version: "2.0",
  name: "Reaction",
  accountRelation: { type: "set", fields: ["cardId"] },  // (작성자, 카드) 유일
  schema: { /* ... */ },
}
```

`single`·`set` 타입은 결정론적 초기 이벤트를 요구하며, SDK가 `createSingleton`/`createInstance`로 구분해 처리합니다.

**판단**: ComposeDB 중단의 영향이 크게 줄어듭니다. **데이터 모델의 의미는 그대로 살고, 표현 문법만 GraphQL SDL에서 JSON `ModelDefinition`으로 바뀝니다.**

따라서 VS-B2′의 후보 순위가 정해집니다.

1. **Ceramic One + Ceramic SDK로 이전** — 유일성·서명·앵커링을 모두 제공함이 확인됨. **기본안**
2. 다른 P2P 문서 저장소 — ①이 막힐 때만 검토
3. libp2p 위 자체 CRDT — 유일성을 직접 구현해야 하므로 최후 수단

VS-B2′의 성격도 바뀝니다. "재선정"이 아니라 **"이전 검증"** 에 가깝습니다. 규모를 L에서 M으로 내립니다.

### 7.4 국내 도메인 DKIM 실태 — 🔴 신규 보안 요구사항

DNS를 직접 조회해 실측했습니다.

**키 길이 (2026-09-21 실측)**

| 도메인 | 셀렉터 | 키 길이 |
|-|-|-|
| github.com | `s1` | 2048 bit |
| yonsei.ac.kr | `google` | 2048 bit |
| kakao.com | `default` | **1024 bit** (`t=y` 테스트 모드) |
| snu.ac.kr | `google` | **1024 bit** |
| **assembly.go.kr (국회)** | `default` | **1024 bit** |

**키 교체는 실재하며 관측 가능하다**

Gmail은 셀렉터 이름이 날짜입니다. 조회 결과 네 개 모두 **폐기 상태**였습니다.

```
20161025._domainkey.gmail.com  →  "k=rsa; p="
20210112._domainkey.gmail.com  →  "v=DKIM1; k=rsa; p="
20221208._domainkey.gmail.com  →  "v=DKIM1; k=rsa; p="
20230601._domainkey.gmail.com  →  "v=DKIM1; k=rsa; p="
```

`p=`가 비어 있으면 **폐기**를 뜻합니다. 구글은 주기적으로 키를 교체하고 구 셀렉터를 폐기 상태로 남깁니다.

**셀렉터는 DNS로 열거할 수 없다**

`naver.com`, `daum.net`, `korea.kr`, `nate.com`은 16종의 흔한 셀렉터로 조회했으나 하나도 나오지 않았습니다. DKIM 셀렉터는 **실제 수신한 메일의 헤더에서만 알 수 있습니다.** DNS에는 열거 수단이 없습니다.

#### 도출되는 요구사항

**(1) 허용 도메인에 2048비트 최소 기준을 적용한다**

1024비트 RSA는 충분한 자원을 가진 공격자가 인수분해할 수 있는 영역입니다. **DKIM 키 하나가 깨지면 그 도메인 사용자를 무제한 위조**할 수 있고, 이는 §신규발견의 레지스트리 탈취와 동일한 결과입니다.

현재 실측 기준으로 이 기준은 **kakao.com, snu.ac.kr, assembly.go.kr을 배제**합니다. 국회 도메인이 배제되는 것은 뼈아프지만, 1024비트 키를 신뢰 기반에 넣는 것은 "수학적으로 검증한다"는 우리 주장과 양립하지 않습니다.

kakao.com이 `t=y`(테스트 모드)인 점도 문제입니다. 테스트 모드 서명은 수신자가 검증 실패를 무시하도록 권고되는 상태이므로, 신원 증명의 근거로 부적절합니다.

**(2) 폐기된 키를 레지스트리에서 반드시 제거한다**

구글이 키를 폐기하는 것은 교체 때문이며, 교체 이유에는 유출 가능성이 포함됩니다. 폐기된 키 해시를 우리 레지스트리에 남겨두면, **그 키를 가진 자가 계속 시민을 찍어낼 수 있습니다.**

즉 `revokeDKIMPublicKeyHash` 호출은 정리 작업이 아니라 **보안 운영 절차**입니다. DNS의 `p=` 비어 있음을 주기적으로 감시해 자동 대응해야 합니다.

기존 시민의 자격은 영향받지 않습니다. 이미 nullifier를 소비했기 때문입니다. 영향받는 것은 신규 가입 경로뿐입니다.

**(3) 레지스트리 초기 구축에 실제 메일 수신이 필요하다**

셀렉터를 열거할 수 없으므로, 허용하려는 각 도메인에서 **실제로 메일을 한 통 받아 헤더를 확인해야** 합니다. 도메인 목록이 늘어날 때마다 반복되는 수작업이며, 자동화하려면 도메인별 계정과 수신 파이프라인이 필요합니다. **운영 비용으로 계획에 반영해야 합니다.**
