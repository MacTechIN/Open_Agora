# 11. 주권 판단 계층 (Sovereign Judgment Layer)

`10_AI_JUDGMENTS.md`는 구조화된 판단이 기존 프롬프트 방식보다 낫다는 것을 보였지만, 상용 API에 의존하면 이 프로젝트의 근간이 여섯 군데에서 무너진다는 것도 함께 보였습니다.

이 문서는 **설계 이득은 전부 유지하면서 그 여섯 가지를 모두 회복하는 구조**를 정의합니다. 결론부터 말하면, 잃어버린 것들은 대부분 **"생성 모델에게 답을 써 달라고 부탁한다"는 선택에서 파생된 것**이었고, 그 선택을 바꾸면 대부분 되돌아옵니다.

---

## 1. 회복 대상

| # | 상용 API에서 잃는 것 | 회복 수단 | 절 |
|-|-|-|-|
| 1 | 탈중앙 — 시민 발언이 외부로 나감 | 자체 호스팅 + 가중치를 IPFS·온체인에 고정 | §5 |
| 2 | 재현성 — G-DETERM 파괴 | 생성이 아닌 **제약 채점** + CPU 정본 구현 | §3, §4 |
| 3 | 가용성 — 외부 장애가 곧 우리 장애 | 3단 캐스케이드 + 장애 시 보류 큐 | §2 |
| 4 | 비용 — 참여자 수 비례 변동비 | 캐스케이드로 LLM 도달률 최소화 | §2 |
| 5 | 한국어 정치 도메인 미검증 | 한국어 특화 모델 유지 + 자체 보정 | §6 |
| 6 | 정치 편향을 검증·수정할 수 없음 | **반사실 불변성 게이트** + 진영별 패리티 | §7 |

여섯 번째가 가장 중요합니다. 나머지 다섯은 엔지니어링 문제지만, 이것은 플랫폼의 존재 이유에 직결됩니다.

---

## 2. 캐스케이드 — 대부분의 글은 LLM에 닿지 않는다

비용과 가용성은 같은 수단으로 동시에 해결됩니다. **무거운 판단에 도달하는 글의 비율을 낮추면** 둘 다 좋아집니다.

```
[사용자 입력]
      │
 T0 ─ 온디바이스 스크리닝 (KcELECTRA-small ONNX, 단말)     ~100%가 통과
      │  · 지연 30ms 미만, 네트워크 불필요, 텍스트가 단말을 떠나지 않음
      │  · score < 0.30 → 종료. 여기서 대다수가 끝난다
      ▼
 T1 ─ 서버 멀티라벨 분류 (kor_unsmile, CPU ONNX)           ~5~10% 도달
      │  · 욕설·혐오 10개 카테고리. 한국어 은어·초성 비하에 강함
      │  · 명백한 무해 → 종료
      ▼
 T2 ─ 의미 판단 (한국어 LLM, 제약 채점)                    ~1~3% 도달
      │  · "비판이 정책을 향하는가 사람을 향하는가"
      │  · 분류기가 할 수 없는 판단만 여기서 한다
      ▼
 T3 ─ 순화문 생성 (한국어 LLM, 생성)                       ~1% 미만
         · T2가 필요하다고 답한 경우에만
```

**T2 도달률이 이 설계의 비용 지표입니다.** 1~3%라면 GPU 한 대로 상당한 규모를 감당합니다. 도달률을 계측해 대시보드에 노출하고, 튀면 T0·T1 임계치를 점검합니다.

### 2.1 장애 시 동작

각 계층은 독립적으로 실패할 수 있습니다. **어떤 경우에도 조용히 통과시키거나 조용히 차단하지 않습니다.**

| 장애 | 동작 |
|-|-|
| T1 불가 | T0 결과만으로 통과시키고 `pending_review`로 표시. 나중에 일괄 재판정 |
| T2 불가 | 경고 없이 통과 + 보류 큐 적재. 디랭킹·감점을 **적용하지 않는다** |
| T3 불가 | 배너는 띄우되 순화문 없이 "직접 수정" 안내만 |

판정 불능을 유해로 취급하면 검열이 되고, 무해로 취급하면 게이트가 무의미해집니다. **보류가 유일하게 정직한 처리입니다.** 보류된 글에는 제재가 소급 적용되지 않습니다. 사용자가 통제할 수 없는 사유이기 때문입니다.

## 3. 핵심 전환 — 생성이 아니라 채점한다

재현성이 깨진 근본 원인은 상용 API라는 사실 자체가 아니라, **모델에게 답을 "쓰게" 했다는 점**입니다. 생성은 샘플링을 수반하고, 샘플링은 시드·온도·커널에 따라 달라집니다.

판단은 생성이 필요 없습니다. **선택지가 이미 정해져 있으므로, 각 선택지의 우도를 계산해 정규화하면 됩니다.**

```
질문: 이 글의 비판은 무엇을 향하는가?
선택지: policy_substance | person_or_party | both | neither

생성 방식:  모델이 토큰을 샘플링해 "person_or_party"라고 씀
            → 시드·온도에 따라 달라짐, 선택지 밖 문자열도 가능

채점 방식:  고정 프롬프트 아래에서 네 선택지 각각의 로그우도를 계산
            logP(policy_substance) = -2.41
            logP(person_or_party)  = -0.34
            logP(both)             = -2.88
            logP(neither)          = -4.12
            → softmax 정규화 → {0.1028, 0.8144, 0.0642, 0.0186}
            → 순전파 한 번. 샘플링 없음. 선택지 밖 출력 불가능
```

| | 생성 | 제약 채점 |
|-|-|-|
| 출력 공간 | 무한 (파싱 필요) | 정확히 우리 선택지 |
| 확률 | 자기 신고 숫자 | 로짓에서 나온 실제 분포 |
| 샘플링 | 있음 (시드 의존) | **없음** |
| 재현성 | 불가 | 가중치·수치 고정 시 가능 |
| 호출 비용 | 출력 토큰만큼 | 순전파 1회 |

Noul은 "예"/"아니오" 두 선택지의 채점, Score는 순서 있는 수준들의 채점으로 같은 방식에 포함됩니다. Score의 기대값은 수준 인덱스의 확률가중 평균입니다.

### 3.1 구현 주의

* **선택지 라벨 길이를 맞춥니다.** 토큰 수가 다르면 긴 라벨이 불리해지므로, 토큰당 평균 로그우도로 정규화하거나 라벨을 단일 토큰에 가깝게 설계합니다.
* **선택지 키는 모델에게 의미를 전달하지 못합니다.** `person_or_party`라는 키가 아니라, criteria에 적은 한국어 설명 문장을 채점 대상으로 씁니다.
* vLLM·llama.cpp 모두 프롬프트 로그확률 반환을 지원하므로 별도 런타임이 필요하지 않습니다.

## 4. 결정론 — 정본과 운영을 분리한다

제약 채점으로 샘플링은 없앴지만 부동소수점 문제가 남습니다. GPU는 리덕션 순서, TF32, 커널 선택에 따라 결과가 미세하게 달라집니다. 같은 GPU·드라이버에서는 재현되지만 다른 하드웨어에서는 보장되지 않습니다.

그래서 **두 경로를 둡니다.**

```
운영 경로 (GPU)                        정본 경로 (CPU)
· 빠르다, 서비스가 쓴다                · 느리다, 누구나 돌릴 수 있다
· fp16/bf16 허용                       · fp32, 배치 1, 결정론 커널
· 정본과 1e-3 이내 일치해야 함          · 분쟁 시 이쪽이 권위를 갖는다
        └──────── 1% 표본 상시 대조 ────────┘
```

* **정본 경로가 권위입니다.** 판정에 이의가 제기되면 CPU 정본으로 재계산한 값이 답입니다.
* 정본 구현은 저장소에 포함하고 누구나 실행할 수 있게 합니다. 느려도 상관없습니다. 검증용이지 서비스용이 아닙니다.
* 운영 경로가 정본과 허용 오차를 넘어 벌어지면 **알람을 올리고 해당 판정을 보류 큐로 보냅니다.**

### 4.1 정본값 양자화

미세한 수치 차이가 기록값과 결정을 바꾸지 않도록, **확률을 소수 4자리로 양자화한 값만 기록하고 정책에 투입합니다.**

```python
canonical = round(probability, 4)   # 0.78341... → 0.7834
```

양자화된 값이 감사 로그의 정본이며, 정책 함수는 이 값만 봅니다. 따라서 결정은 기록된 값으로부터 **완전히 재계산 가능**합니다. GPU와 CPU가 4자리에서 갈리면 그것은 조용한 오차가 아니라 감지된 불일치이고, 보류 처리됩니다.

### 4.2 판정 기록에 포함하는 것

```json
{
  "input_hash": "sha256:…",           
  "weights_cid": "bafy…",             
  "tokenizer_hash": "sha256:…",       
  "prompt_template_hash": "sha256:…", 
  "option_set_hash": "sha256:…",      
  "judgments": { "attack_target": { "probabilities": {...}, "choice": "…" } },
  "policy": { "attack_review": 0.35, "attack_action": 0.70, "severity_block": 2.0 },
  "engine": { "path": "gpu", "verified_against_canonical": true }
}
```

이 여섯 개 해시가 있으면 제3자가 **완전히 동일한 조건을 재구성**할 수 있습니다. 프롬프트 템플릿과 선택지 집합까지 해시하는 이유는, 이것들이 바뀌면 같은 가중치라도 다른 판단이 나오기 때문입니다. 조용한 프롬프트 수정은 조용한 정책 변경과 같습니다.

## 5. 모델 주권 — 판단자도 앵커링한다

시민의 글은 IPFS에 영구 보존하고 온체인에 앵커링하면서, **그 글을 판정하는 모델은 운영자만 아는 상태**라면 감사는 절반짜리입니다.

따라서 판단 모델을 데이터와 동일하게 취급합니다.

* 가중치·토크나이저·프롬프트 템플릿·선택지 집합을 **IPFS에 고정(pin)** 하고 CID를 얻습니다.
* CID를 **온체인 앵커에 기록**합니다. 안건 상태 머클 루트와 같은 트랜잭션에 실을 수 있습니다.
* 모든 판정 로그가 `weights_cid`를 참조하므로, **어느 시점에 어떤 모델이 판정했는지 위조할 수 없습니다.**

### 5.1 모델 교체는 거버넌스 사건이다

모델을 바꾸는 것은 판정 기준을 바꾸는 것이고, 이는 임계치 변경보다 무겁습니다.

1. 새 모델의 **편향 감사 결과를 먼저 공개**합니다 (§7).
2. 최소 14일 공지 기간을 둡니다.
3. 새 CID를 온체인에 앵커링합니다.
4. 교체 전후 기간의 판정은 로그의 `weights_cid`로 구분됩니다.
5. **과거 판정을 소급 재적용하지 않습니다.** 새 모델이 더 엄격하다고 해서 과거 글을 다시 처벌하면 사후입법이 됩니다.

## 6. 보정을 우리가 소유한다

상용 모델은 보정(calibration)을 학습했다고 주장하지만, 그 주장은 그들의 도메인에 대한 것입니다. 우리 도메인에서의 보정은 어차피 우리가 확인해야 합니다. 그렇다면 **처음부터 우리가 소유하는 편이 낫습니다.**

1. **평가셋 구축** — 한국어 정치 게시물 1,000건에 `attack_target`·`norm_severity`를 사람이 라벨링합니다. 라벨러의 정치 성향을 균형 있게 구성하고, 항목당 3인 이상이 독립 라벨링해 일치도(Krippendorff's α)를 보고합니다. **α가 낮으면 모델 문제가 아니라 질문 정의 문제입니다.** 그때는 criteria를 다시 씁니다.
2. **온도 보정** — 검증셋에서 로짓 온도 $T$를 학습해 신뢰도 곡선을 맞춥니다. 단일 파라미터이므로 과적합 위험이 낮고, $T$는 판정 기록에 포함됩니다.
3. **임계치 재설정** — 0.35 / 0.70 / 2.0은 남의 문서에서 온 예시값입니다. 보정 후 우리 데이터의 비용 곡선에서 다시 정합니다.
4. **평가셋 공개** — 개인정보를 제거한 평가셋과 결과를 공개합니다. 누구나 우리 주장을 재검증할 수 있어야 합니다.

## 7. 편향 게이트 — 이 설계의 핵심

판단 모델에 정치적 편향이 있으면, 진영 편향을 없애려고 만든 플랫폼이 편향된 심판을 쓰게 됩니다. 이것은 성능 지표가 아니라 **배포 차단 조건**이어야 합니다.

새 게이트 **G-BIAS**를 정의하고 `09_DEVELOPMENT_PLAN.md`의 게이트 목록에 추가합니다.

### 7.1 반사실 불변성 (Counterfactual Invariance)

가장 강력한 검사입니다. 같은 문장에서 **정당·인물 고유명사만 바꾸고 나머지를 그대로 둔 쌍**을 만듭니다.

```
원문 : "A당의 이번 법안은 현장 비용을 전혀 계산하지 않은 탁상행정이다."
반사실: "B당의 이번 법안은 현장 비용을 전혀 계산하지 않은 탁상행정이다."

요구: |judgment(원문) − judgment(반사실)| ≤ ε   (모든 판단 항목에 대해)
```

두 문장은 **정치적으로 동일한 수준의 발언**입니다. 판단이 달라진다면 그것은 문장이 아니라 정당 이름에 반응한 것이고, 정의상 정치 편향입니다.

* 평가셋의 모든 항목에 대해 정당 조합을 순환시켜 쌍을 생성합니다.
* `ε = 0.05`(확률), Score는 `0.2`(수준)를 잠정 기준으로 하되 §6의 보정 후 재설정합니다.
* **위반 항목이 하나라도 임계를 넘으면 배포가 막힙니다.**

이 검사는 자동 생성이 가능하고 CI에서 돌릴 수 있습니다. 라벨링이 추가로 필요하지 않다는 점도 큽니다.

### 7.2 진영별 성능 패리티

라벨링된 평가셋에서 스탠스별로 나눠 봅니다.

| 지표 | 요구 |
|-|-|
| 위양성률(FPR) — 무해한 글을 유해로 판정 | SUPPORT과 OPPOSE 간 차이 ≤ 3%p |
| 위음성률(FNR) | 차이 ≤ 3%p |
| `attack_target` 분포 | 스탠스별 분포 차이가 라벨 분포 차이를 넘지 않을 것 |

한쪽 진영의 어법에서만 오탐이 높다면, 그 모델은 배포할 수 없습니다.

### 7.3 운영 중 상시 감시

배포 전 검사만으로는 부족합니다. 실제 글의 분포는 평가셋과 다릅니다.

* 주간으로 스탠스별 `COACH` 비율과 판단값 분포를 비교해 공개합니다.
* 차이가 유의하게 벌어지면 조사 대상입니다. 원인은 모델 편향일 수도 있고, 실제로 한쪽 어법이 거칠어진 것일 수도 있습니다. **판단값이 로그에 있으므로 구분이 가능합니다.**
* 이 통계는 월간 투명성 보고서에 포함합니다.

## 8. 어댑터 경계 — TypeSafe의 자리

판단 실행자를 교체 가능한 인터페이스 뒤에 둡니다. 정책·감사·게이트는 실행자와 무관하게 동일합니다.

```python
class JudgmentEngine(Protocol):
    """판단 실행자. 정책과 감사 계층은 이 경계 뒤를 알지 못한다."""

    name: str
    reproducible: bool   # 정본 재계산이 가능한가

    def judge(self, state: Mapping, questions: Mapping) -> EngineResult: ...
```

| 구현 | 재현 가능 | 운영 투입 | 용도 |
|-|-|-|-|
| `LocalScoringEngine` (GPU) | 정본 대조로 보장 | ✅ 기본값 | 서비스 |
| `CanonicalCpuEngine` | ✅ 정의상 정본 | 검증 전용 | 이의 제기 재계산, 1% 대조 |
| `TypeSafeEngine` | ❌ | ⬜ 평가 한정 | 자체 모델 성능의 기준선 |
| `NullEngine` | — | 장애 시 | 보류 큐로 우회 |

**TypeSafe의 역할은 기준선입니다.** 자체 모델이 좋은지 나쁜지 판단하려면 비교 대상이 필요하고, 잘 보정된 상용 모델은 좋은 비교 대상입니다. 평가셋에 대해 두 엔진을 같은 지표로 측정해 격차를 봅니다.

**운영에 투입하려면 별도 조건을 만족해야 합니다.** 판정 로그에 `reproducible: false`와 `engine: typesafe`가 명시되고, 해당 판정은 디랭킹·감점에 쓰이지 않으며(재현 불가한 근거로 제재할 수 없으므로), 사용자에게 외부 전송 사실이 고지되어야 합니다. 이 조건 아래에서는 §1의 여섯 가지가 모두 유지됩니다.
