# 16. 블록체인 도입 — 무엇을, 언제, 어떻게

현재 배포는 공유 서버만 씁니다. 블록체인은 한 줄도 쓰지 않습니다. 이 문서는 **그것을 언제 어떻게 바꾸는지**를 구체적인 서비스·비용·순서로 적습니다.

관련: `12_ONCHAIN_DEPENDENCIES.md`(무엇을 쓸 것인가), `15_BRIDGE_SERVER.md`(지금의 한계)

---

## 1. 블록체인이 실제로 하는 일

막연히 "블록체인을 쓴다"가 아니라, **무엇을 못 하게 만드는가**로 적습니다.

| 지금 가능한 일 | 블록체인이 막는 방식 |
|-|-|
| 운영자가 글 내용을 고친다 | 글마다 작성자 서명 → 고치면 검증 실패 |
| 운영자가 글을 지운다 | 주기적 머클 루트 앵커링 → 사라진 글이 대조에서 드러남 |
| 운영자가 과거 기록을 소급 조작한다 | 앵커가 시각과 함께 체인에 박힘 |
| 한 사람이 계정을 여러 개 만든다 | Nullifier 레지스트리 → 이메일당 하나 |

**막지 못하는 것도 분명히 합니다.**

* 애초에 사실과 다른 글이 올라오는 것 — 블록체인은 "바뀌지 않았음"만 증명한다
* 운영자가 특정 글을 화면에 안 보여주는 것 — 다만 앵커에는 있으므로 **숨긴 사실이 드러난다**
* 서버가 멈추는 것 — 이것은 P2P(VS-B1)가 해결한다

---

## 2. 순서가 중요하다

**서명이 앵커링보다 먼저입니다.** 순서를 바꾸면 절반만 작동합니다.

서명 없이 앵커링만 하면 "이 묶음의 해시"만 체인에 남습니다. 운영자가 글 하나를 고치면 해시가 달라지니 **무언가 바뀌었다는 것은** 알지만, **어느 글이 어떻게 바뀌었는지**는 알 수 없습니다. 서명이 있으면 그 글 하나를 특정할 수 있습니다.

```
1단계  작성자 서명        → 고친 글이 특정된다
2단계  머클 루트 앵커링    → 지운 글과 소급 변경이 드러난다
3단계  1인 1계정 (Semaphore) → 다중 계정을 막는다
4단계  데이터 정본 이전 (P2P) → 서버가 멈춰도 산다
```

1·2단계만 끝나도 성격이 바뀝니다. 운영자가 여전히 고칠 수는 있지만 **고친 사실이 드러나므로, 신뢰의 문제가 검증의 문제가 됩니다.**

---

## 3. 단계별 구현

### 1단계 — 작성자 서명 (VS-A4)

블록체인이 필요 없습니다. 이미 있는 것으로 됩니다.

* 각 기기에 이미 P-256 키가 있습니다(Windows TPM, Android Keystore).
* 웹은 브라우저 WebCrypto 키를 씁니다.
* 글을 올릴 때 내용 해시에 서명하고, 서명을 함께 저장합니다.
* 누구나 글 옆의 「검증」을 눌러 서명을 확인할 수 있습니다.

**비용 0원. 외부 서비스 불필요.** 가장 먼저 해야 하는 이유입니다.

### 2단계 — 머클 루트 앵커링 (VS-F6)

**사용자는 아무것도 하지 않습니다.** 지갑도 가스비도 필요 없습니다. 서버가 6시간마다 한 번 트랜잭션을 보냅니다.

| 항목 | 내용 |
|-|-|
| 방식 | 그 기간의 모든 글 해시로 머클 트리 → 루트 하나만 기록 |
| 체인 | Arbitrum One 또는 Base (L2) |
| 빈도 | 6시간마다 = 하루 4회 = 월 120회 |
| 비용 | 트랜잭션당 수십 원 → **월 수천 원 수준** |
| 검증 | 누구나 글의 머클 증명을 받아 체인의 루트와 대조 |

앵커링은 **글 하나하나를 체인에 올리는 것이 아닙니다.** 수천 건을 해시 하나로 묶어 그것만 올립니다. 그래서 싸고, 글이 늘어도 비용이 거의 안 늘어납니다.

구현은 직접 컨트랙트를 쓸 필요도 없습니다. 선택지가 둘입니다.

* **Ceramic self-anchoring** — 데이터 계층이 앵커링을 포함합니다(`12_ONCHAIN_DEPENDENCIES.md` §3.2). 3단계와 함께 가면 별도 작업이 없습니다.
* **직접 앵커링** — 저장용 컨트랙트 하나(수십 줄)를 배포하고 서버가 호출. Ceramic 이전을 기다리지 않고 먼저 할 수 있습니다.

**먼저 하려면 직접 앵커링이 빠릅니다.** Ceramic 재선정(VS-B2′)이 아직 끝나지 않았기 때문입니다.

### 3단계 — 1인 1계정 (Semaphore + ZK-Email)

지금은 이메일 인증으로 막고 있지만, **인증 순간 서버가 이메일과 신원을 동시에 봅니다.** 저장하지 않는다는 약속을 믿어야 합니다. 이 단계가 그 믿음을 없앱니다.

이미 배포된 것을 씁니다. 직접 만들지 않습니다.

| 쓰는 것 | 왜 |
|-|-|
| **zk-email 회로** | DKIM 서명을 영지식으로 검증. 검증된 회로를 그대로 쓴다 |
| **Semaphore** | Arbitrum·Polygon 등에 이미 배포됨. **400명 이상이 참여한 세리머니**를 물려받는다 |
| 우리 컨트랙트 | Nullifier 집합 하나. 함수 하나짜리 |

**자체 신뢰 설정(trusted setup)을 하지 않는 것이 핵심입니다.** 소규모 팀이 세리머니를 운영하면 부산물이 남았는지를 아무도 검증할 수 없고, 남아 있으면 가짜 시민을 무제한 만들 수 있습니다(`12_ONCHAIN_DEPENDENCIES.md` §2).

**사용자 경험**: 가입할 때 인증 메일을 받는 것까지는 지금과 같습니다. 다른 점은 **증명이 기기 안에서 만들어지고 서버는 이메일을 보지 못한다**는 것입니다. 지갑은 필요 없고, 온체인 등록은 서버가 대신 제출합니다.

### 4단계 — 데이터 정본 이전 (VS-B2′, VS-B1)

여기까지 오면 서버는 **읽기 게이트웨이**가 됩니다. 정본은 P2P에 있고, 서버가 멈춰도 참여자끼리 동기화됩니다. 브라우저는 여전히 게이트웨이를 거치지만, 누구나 자기 게이트웨이를 띄울 수 있으므로 중앙화 지점이 아닙니다.

이 단계는 ComposeDB 중단으로 재선정 중입니다(`13_VS_C0_FINDINGS.md` §7.3에서 Ceramic One으로 가는 길이 열려 있음을 확인).

## 4. 비용 정리

| 단계 | 초기 | 운영 |
|-|-|-|
| 1. 작성자 서명 | 0원 | 0원 |
| 2. 앵커링 | 컨트랙트 배포 수만 원 | **월 수천 원** |
| 3. 1인 1계정 | 컨트랙트 배포 수만 원 | 가입당 수십 원 (서버 부담) |
| 4. P2P 이전 | 0원 | 부트스트랩·릴레이 노드 운영비 |

**사용자는 어느 단계에서도 지갑이나 가스비가 필요 없습니다.** 일반 시민에게 지갑을 요구하면 그 자체가 진입 장벽이 되고, 이 플랫폼은 진입 장벽을 낮추는 것이 목적입니다.

## 5. 권고 순서

**1단계(서명)를 지금 바로 합니다.** 비용이 없고 외부 의존이 없으며, `15_BRIDGE_SERVER.md`가 적은 취약점 중 가장 무거운 것을 없앱니다.

**2단계(앵커링)를 그다음에 합니다.** 월 수천 원으로 "지운 글이 드러난다"를 얻습니다. Ceramic 재선정을 기다리지 않고 직접 앵커링으로 먼저 합니다.

**3단계는 VS-C0 잔여 확인이 끝난 뒤**입니다. Semaphore 세리머니 전사본 위치, 국내 도메인 DKIM 키 길이(2048비트 미만 배제) 확인이 남아 있습니다(`13_VS_C0_FINDINGS.md` §9).

**4단계는 데이터 계층 재선정 이후**입니다.
