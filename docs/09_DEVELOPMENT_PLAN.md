# 09. 개발계획서 — 마이크로프로세스 수직 적층 (Vertical Stackable)

본 문서는 `07_ROADMAP.md`의 기간 중심 로드맵을 **실행 단위**로 분해한 것입니다. 로드맵이 "언제 무엇을"이라면, 이 문서는 "무엇을 어떤 순서로 쌓아 올리는가"입니다.

---

## 1. 방법론

### 1.1 수직 슬라이스란

이 시스템은 UI · 바인딩 · 코어 · P2P · 연산 · 온체인 5개 층으로 구성됩니다. 층 단위로 개발하면(수평 분할) 모든 층이 끝날 때까지 **아무것도 동작하지 않고**, 통합 시점에 설계 결함이 한꺼번에 터집니다. 특히 P2P·ZK·ML이 뒤섞인 이 프로젝트에서는 치명적입니다.

따라서 매 작업 단위를 **모든 층을 관통하는 얇은 수직 절편**으로 자릅니다.

```
        VS-A3        VS-B1        VS-E3        ← 각 슬라이스는 세로로 관통
          │            │            │
  L5 UI   ■            ■            ■
  L4 바인딩 ■            ■            ■
  L3 코어   ■            ■            ■
  L2 데이터 ·            ■            ■
  L1 체인   ·            ·            ·
          ↓            ↓            ↓
       동작하는     동작하는      동작하는
       제품 v0.1    제품 v0.2     제품 v0.3
```

### 1.2 적층(Stackable) 원칙

1. **모든 슬라이스는 데모 가능하다.** 완료 시점에 사람이 앱을 열어 눈으로 확인할 수 있어야 합니다. "라이브러리만 붙였다"는 슬라이스가 아닙니다.
2. **하위 슬라이스를 무너뜨리지 않는다.** 새 슬라이스가 이전 슬라이스의 수용 기준을 깨면 미완성입니다.
3. **스텁은 명시하고 교체를 예약한다.** 초기 슬라이스는 반드시 스텁을 씁니다. 어떤 스텁이 어느 슬라이스에서 실물로 바뀌는지 §5 교체 원장에 기록합니다.
4. **가장 위험한 것을 먼저 세로로 뚫는다.** ZK 증명 성능, NAT 통과율, 몰표 무력화는 실패 시 설계를 되돌려야 하는 항목이므로 앞쪽 스택에 배치합니다.

### 1.3 슬라이스 규격

각 슬라이스는 아래 항목을 모두 채워야 시작할 수 있습니다.

| 항목 | 의미 |
|-|-|
| **관통 층** | 이 슬라이스가 건드리는 층 (L1~L5) |
| **선행** | 반드시 완료되어야 하는 슬라이스 |
| **스텁** | 이번에는 가짜로 두는 것 |
| **데모** | 완료 시 사람이 보게 되는 것 |
| **수용 기준** | 통과/실패를 기계적으로 판정할 조건 |
| **규모** | S(≤1일) · M(2~3일) · L(4~5일) |

### 1.4 불변식 게이트

**모든 슬라이스는 병합 전 아래 검사를 통과해야 합니다.** 해당 없으면 생략이 아니라 "해당 없음"을 명시합니다.

| 게이트 | 검사 |
|-|-|
| **G-BRIDGE** | 랭킹·반응·평판을 건드렸다면, 합성 몰표 주입 시 $b_i$가 상승하지 않는가 (→ VS-F2) |
| **G-PRIV** | 실명·이메일·`f_u`·반응자 신원이 새 경로로 노출되지 않는가 (INV-1~5) |
| **G-IMMUT** | 삭제 경로를 만들지 않았는가. 노출 조정만인가 (D3) |
| **G-DETERM** | 배치 잡이라면 스냅샷 해시·모델 버전·시드를 산출물에 기록하는가 |
| **G-PARITY** | 코어 인터페이스 변경 시 Kotlin·C# 바인딩이 `uniffi`로 함께 생성되었는가 |
| **G-BIAS** | 판단 모델을 바꿨다면, 반사실 쌍(정당명만 교체)의 판단이 불변이고 진영별 오류율 격차가 허용 범위인가 (→ `11_SOVEREIGN_JUDGMENT.md` §7) |

## 3. 슬라이스 상세

### Stack A — 골격 (Walking Skeleton)

목표: 5개 층을 관통하는 가장 얇은 경로를 먼저 뚫어, 이후 모든 슬라이스가 올라탈 바닥을 만듭니다.

#### VS-A1 · 모노레포와 코어 호출
* **관통 층** L5·L4·L3 | **선행** 없음 | **규모** M
* **스텁** 코어는 `version()` 하나만 노출
* **데모** Windows 앱과 Android 앱을 각각 실행하면 화면에 코어 버전 문자열이 뜬다
* **수용 기준** `civicagora.udl`에서 생성된 Kotlin·C# 바인딩으로 호출 성공. CI가 Windows x64, Android arm64/x64 크로스 컴파일 통과
* **게이트** G-PARITY

#### VS-A2 · 로컬 신원 생성
* **관통 층** L5·L4·L3 | **선행** A1 | **규모** M
* **스텁** ZK 증명 없음. 검증 없이 키만 생성
* **데모** 앱 첫 실행 시 키페어가 생성되고 내 DID가 화면에 표시된다. 재실행해도 같은 DID가 유지된다
* **수용 기준** 개인키가 Android Keystore / Windows Hello에 저장되고 앱 메모리로 평문 노출되지 않음. 앱 삭제 후 재설치 시 새 DID 발급
* **게이트** G-PRIV

#### VS-A3 · 로컬 카드 작성과 조회
* **관통 층** L5·L4·L3 | **선행** A2 | **규모** L
* **스텁** P2P 없음(로컬 SQLite만). 서명 없음. 톤 코칭 없음
* **데모** 3단 구조화 입력(150/200/150)으로 카드를 쓰면 목록에 나타난다. 글자 수 초과가 차단된다
* **수용 기준** 필드별 길이 검증, 근거 URL 필수 검증 동작. 앱 재시작 후에도 카드 유지
* **게이트** G-IMMUT (삭제 버튼을 만들지 않았는가)

#### VS-A3-iOS · iOS 앱 골격

**산출**: `apps/ios/`. SwiftUI, Secure Enclave P-256, 공유 API 연결. 화면 구성은 Android 와 같습니다.

**데모**: 맥에서 `make bootstrap` 후 시뮬레이터에서 광장이 보이고, 실기기에서 DID 가 Secure Enclave 로 표시되며, 앱을 껐다 켜도 같은 DID 가 나온다.

**CI 에서 빌드하지 않습니다.** 맥 러너는 리눅스의 10배 단가이고, TestFlight 배포 단계에 가서 붙이는 편이 낫습니다. 그 전까지는 맥에서 손으로 확인합니다.

**상태**: 코드는 있으나 **컴파일된 적이 없습니다.** 맥이 확보되기 전까지 완료로 세지 않습니다.

#### VS-A4 · 문서 서명과 검증 · **완료 (2026-09-22)**
* **관통 층** L4·L3 | **선행** A3 | **규모** M
* **데모** 저장된 글을 데이터베이스에서 직접 고치면 화면이 「⚠ 서명 불일치」로 표시한다
* **수용 기준** 새로 올라오는 글이 작성자 DID로 서명됨. 서명 불일치는 **저장 단계에서 거절**
* **게이트** G-PARITY, 서명 벡터 대조(`web/scripts/check-signing.mjs`)

**확인된 것** (`web/scripts/e2e-signing.mjs`, 실제 서버·DB 대상 7건)

1. 서명한 주제가 등록되고 서명이 저장된다 (주제·첫 의견 모두)
2. 내용이 바뀐 서명을 거절한다
3. 시각이 바뀐 서명을 거절한다
4. 기기 시계가 ±5분을 벗어나면 거절한다
5. 서명 없는 글은 아직 받는다(전환기)

**렌더링 거부 대신 표시로 바꿨습니다.** 원래 기준은 "서명 불일치 시 렌더링
거부"였으나, 그러면 **운영자가 글을 고쳐서 숨길 수 있게 됩니다** — 고친 글이
화면에서 사라지는 것은 지운 것과 같습니다. 대신 불일치를 눈에 띄게 표시하고,
저장 단계에서 거절합니다.

**함께 고친 것**: 코어와 서버의 식별자 계산 규칙이 서로 달랐습니다. 지금까지는
서버만 식별자를 만들어 드러나지 않았으나, 첫 의견의 서명이 주제 식별자를
덮으면서 문제가 됩니다. 규칙을 하나로 맞추고 공용 벡터로 묶었습니다.

### Stack B — P2P 전파 ★

목표: **NAT 통과율**이라는 최대 기술 위험을 조기에 실측합니다. 여기서 실패하면 릴레이 의존도를 재설계해야 하므로 Stack C보다 먼저 배치합니다.

#### VS-B1 · 같은 네트워크 두 기기 간 전파
* **관통 층** L5·L3·L2 | **선행** A4 | **규모** L
* **스텁** Ceramic 없음(libp2p 직접 전송). 안건 개념 없음(단일 토픽)
* **데모** 같은 Wi-Fi의 Android 기기에서 카드를 쓰면 Windows PC 목록에 수 초 내 나타난다
* **수용 기준** mDNS 피어 발견 + GossipSub 전파. 서명 검증 통과한 카드만 수용
* **게이트** G-PARITY

#### VS-B2′ · Ceramic One 이전 검증 ★
* **관통 층** L2 | **선행** B1 | **규모** M
* **배경** ComposeDB가 사실상 중단됐다(마지막 릴리스 2024-02-27). 기존 VS-B2는
  착수할 수 없다 (→ `13_VS_C0_FINDINGS.md` §2)
* **데모** 후보 3종을 비교한 선정 보고서와, 선정안으로 카드를 저장·조회하는 프로토타입
* **수용 기준** Ceramic One SDK에서 네 모델을 정의하고, `Reaction`이
  `accountRelation: { type: "set", fields: ["cardId"] }`로 **(작성자, 카드)
  유일성을 실제로 거부하는지** 테스트로 확인한다
* **비고** 유일성 강제는 Ceramic One에 보존됨이 확인됐다(→ `13_VS_C0_FINDINGS.md`
  §7.3). 따라서 이 슬라이스는 재선정이 아니라 이전 검증이며, 바뀌는 것은
  표현 문법(GraphQL SDL → JSON ModelDefinition)이지 데이터 모델의 의미가 아니다.
  유일성 거부가 실제로 동작하지 않으면 그때 후보 ②③으로 되돌아간다

#### VS-B2 · 선정안 영속화
* **관통 층** L3·L2 | **선행** B2′ | **규모** L
* **데모** 두 기기를 모두 끈 뒤 새 기기로 접속해도 기존 카드가 전부 보인다
* **수용 기준** `Policy`/`DebateCard` 모델이 ComposeDB에 정의되고 스트림 검증 통과
* **게이트** G-IMMUT

#### VS-B3 · NAT 통과 ★
* **관통 층** L3·L2 | **선행** B2 | **규모** L
* **데모** 가정용 공유기 하위의 LTE Android 기기와 다른 네트워크의 Windows PC가 **릴레이 없이 직접** 카드를 주고받는다
* **수용 기준** AutoNAT 도달성 판정 → DCUtR 홀펀칭 성공률 측정. **실패 시 Circuit Relay v2 폴백이 100% 동작**. 측정 결과를 문서화
* **위험 대응** 홀펀칭 성공률이 50% 미만이면 릴레이 노드 운영 규모를 재산정하고 `01_ARCHITECTURE.md` §5를 갱신

#### VS-B4 · 오프라인 작성 큐
* **관통 층** L5·L4·L3 | **선행** B3 | **규모** M
* **데모** 비행기 모드에서 카드를 작성하면 "전송 대기" 표시가 뜨고, 네트워크 복구 시 자동 전파된다
* **수용 기준** 큐 영속화. 중복 전송 없음. 앱 강제 종료 후에도 큐 유지

#### VS-B5 · 부분 복제와 용량 상한
* **관통 층** L5·L3·L2 | **선행** B4 | **규모** M
* **데모** 설정에서 블록스토어 상한(기본 500MB)을 조절할 수 있고, 초과 시 오래된 블록이 정리된다
* **수용 기준** 구독 안건만 복제. LRU 제거. "전체 노드 모드"는 Wi-Fi + 충전 중에만 활성

### Stack C — 신원 ★

목표: **ZK 증명 성능**이라는 두 번째 고위험 항목을 실측합니다. 모바일에서 너무 느리면 가입 자체가 불가능합니다.

#### VS-C1 · 증명 생성과 아티팩트 고정 ★
* **관통 층** L3 | **선행** A2 | **규모** L
* **스텁** 온체인 없음. 로컬 검증만
* **변경** 자체 신뢰 설정을 하지 않는다. zk-email 회로와 Semaphore 아티팩트를
  쓰되 **런타임 다운로드 경로를 코드에서 제거**하고 저장소에 고정, 해시 기록,
  IPFS 고정 + 온체인 CID 앵커링한다. 기본 동작은 외부 CDN(`snark-artifacts.pse.dev`)
  에서 내려받는 것이며, 그대로 두면 CDN 장애가 신규 가입 전면 중단으로 이어진다
  (→ `13_VS_C0_FINDINGS.md` §7.2)
* **착수 조건 해소** 세리머니 400명+ 완료 확인(2024-07-13, 이더리움 블록 20300394)
* **데모** 실제 수신한 인증 메일 파일로 증명을 생성하고 검증에 성공한다. **Android 실기기 증명 생성 시간을 초 단위로 출력**한다
* **수용 기준** DKIM RSA 서명 검증 회로 동작. `Nullifier = Poseidon(Email, AppSalt)` 산출. **rapidsnark 기준 5초 이내**
* **위험 대응** 5초를 넘기면 회로 최적화 또는 증명 체계 변경(Groth16 → Plonk 등)을 검토. 이 슬라이스 실패는 `02_IDENTITY_PRIVACY.md` 재설계를 의미

#### VS-C2 · Nullifier 컨트랙트와 그룹 연동
* **관통 층** L3·L1 | **선행** C1 | **규모** M
* **착수 막힘 (2026-09-23)** 허용 도메인 목록을 채울 수 없습니다. Gmail·네이버·
  다음·네이트의 DKIM 셀렉터가 DNS로 조회되지 않으며, 셀렉터는 원래 DNS로

**필명으로 셉니다.** DID로 세면 한 사람이 다섯 몫을 행사합니다(D21). 그렇다고
사람 식별자로 세면 누가 무엇을 눌렀는지가 남습니다. `Poseidon(비밀, 고정 scope)`
로 만든 필명이 둘 다 풉니다 — 비밀에 묶여 위조할 수 없고, 이메일·DID와는
이어지지 않습니다.

**고정 scope를 쓰는 이유**는 브리징 때문입니다. 행렬 분해
$\hat r(u,i) = \mu + b_u + b_i + f_u \cdot f_i$는 사람별 행을 요구하므로 한
사람의 반응들이 서로 묶여야 합니다. 지지(VS-C3a)가 주제마다 다른 scope를 쓰는
것과 반대이며, 목적이 다르면 scope도 다릅니다.

**확인된 것** (`web/scripts/e2e-reactions.mjs`, 실제 서버·DB 대상 12건)

1. 반응이 집계되고 **바꿀 수 있다**
2. **지나간 증명을 다시 보내 남의 반응을 되돌릴 수 없다** — 증명이 시각을 묶고
   서버가 앞선 시각을 거부한다
3. 다른 카드의 증명을 옮겨 붙일 수 없고, 증명과 다른 종류도 거절된다
4. 한 사람의 필명이 카드 간에 같다 — 브리징 행렬의 전제
5. 화면에 필명이 실리지 않는다

**아직 못 막는 것 — 자기 카드에 반응하기**

명세 §5는 자기 카드에 반응할 수 없다고 합니다. 그런데 카드의 작성자는 DID로,
반응자는 필명으로 표시되고 **둘은 의도적으로 이어져 있지 않습니다.** 서버는
둘이 같은 사람인지 알 수 없습니다. 지금은 화면에서만 막으므로 우회할 수
있습니다.

서버에서 막으려면 카드를 올릴 때도 영지식 증명을 받아야 하고, 그러면 네이티브
앱이 Semaphore를 갖추기 전까지 글을 올릴 수 없게 됩니다. 그래서 *부분* 완료로
둡니다.

**웹에만 있습니다.** 네이티브 앱은 Semaphore가 코어에 들어간 뒤에 붙습니다.

   성립합니다. 시험 카드 하나만 주면 추정할 근거가 없습니다

29개 시험이 데이터 4벌·배수 4종에서 성질을 확인합니다. 배수 1·5에서 **깨지는

## 8. 진행 관리

### 8.1 슬라이스 상태

`대기` → `진행` → `데모 대기` → `완료`. **"데모 대기"를 건너뛸 수 없습니다.** 코드가 병합되어도 데모로 확인되기 전에는 완료가 아닙니다.

**실제 진행 상황은 [`17_STATUS.md`](./17_STATUS.md)에 있습니다.** 이 문서는 계획이고 그쪽이 실측이므로, 둘이 어긋나면 그쪽이 사실입니다.

2026-09-22 기준으로 계획에서 벗어난 두 가지를 여기에 적어 둡니다.

**1. Stack B(P2P)보다 공유 서버와 웹앱을 먼저 만들었습니다.**

P2P는 같은 네트워크의 두 기기가 서로를 찾는 것부터 시작합니다. 그 단계에서는 아무도 쓸 수 없고, 쓸 수 없으면 무엇이 틀렸는지도 모릅니다. 공유 서버는 임시 발판이며 벗어나는 순서는 `15_BRIDGE_SERVER.md`에 있습니다. **대가는 분명합니다** — 지금 서버는 데이터베이스 접근 권한만 있으면 글을 지울 수 있고, 그것은 불변성이 아닙니다. VS-A4 → VS-F6 → Stack B 순서로 갚습니다.

**2. VS-A3′(주제 계층)이 계획에 없던 슬라이스로 추가되었습니다.**

원래 VS-A3은 카드만 다뤘습니다. 실제로 써 보니 **주제 없이 의견만 올리는 화면**이 나왔고, 그것은 공론이 아니었습니다. 찬반은 주제가 아니라 쟁점 질문에 대한 것이라는 D16, 입장에 따라 묻는 말이 바뀐다는 D17이 여기서 나왔습니다.
